# 独自ブログ：現行設計書

最終更新：2026-10-19。現行の要件、採用構成、比較と選定理由をまとめる。提案・未決と記した項目は採用済みではない。

## 1. この文書の読み方

- **要望・決定**：本人から提示・選択されたもの。
- **提案**：要望を満たすための設計候補。今回の文書化で合意済みにしない。
- **実装済み**：現在のコードが持つ動作。採用承認とは区別する。
- **未決・未実装**：判断や作業が残るもの。

本書は現行仕様・責務・設計理由の正本とする。進捗と未完了事項は[公開台帳](blog-publication-roadmap-2026-10-18.md)、画面の採用仕様と理由は[UI設計](ui-ux-decisions-current.md)を参照する。実装と要望の差は修正課題として扱い、実装に合わせて要望を変更しない。個別のコード定数は現状値であり、恒久的な要件ではない。

## 2. 目的・範囲・決定事項

目的は、自分のドメインで自作記事と外部媒体の本人記事を案内し、継続して執筆・運用できるサイトを作ること。学習を兼ね、設計・コード・UI/UXの判断理由、比較案、検証結果、LLM利用を説明できる記録を残す。技術面接のためだけに複雑な機能を増やさない。

| ID | 要望・決定 | 設計上の扱い（実装進捗は公開台帳） |
|---|---|---|
| R01 | Markdownとプレビューで自作記事を執筆 | 編集・プレビュー並列を採用。実装・受入の状態は公開台帳C2/C3/R4 |
| R02 | 自作記事とnote・Qiita・Wantedlyのリンクを元の公開日順に混在 | 自作記事と元記事リンクを案内し、元公開日で統合する。本文転載は求めない |
| R03 | 外部記事をできれば自動登録 | 自動同期を設計対象とし、黙って手動へ変更しない |
| R04 | SSRで本文HTMLを取得可能にする | JavaScriptを実行せず公開本文を取得できること |
| R05 | React／TypeScript、TanStack Router、Goを使用 | 現在はTanStack StartによるSSRとGo API |
| R06 | 常時稼働。意図的なアイドル停止を避ける | AWSサービスを通常各1タスク維持。容量の最終値は負荷検証で判断 |
| R07 | AWSを軸に、実行基盤はECS＋Fargate | 決定済み。最安を意味しない |
| R08 | 変更内容に応じたバックアップと復元 | 変更時の取得と別環境への復元を対象とし、毎日の自前フルダンプを既定にしない |
| R09 | 個人GitHubの非公開リポジトリで管理 | course-k/course-k-blog。変更はブランチとPR |
| R10 | UI/UXを本人と検討し、選択理由を記録 | 一覧・本文の文字組み・目次・管理配置・外部別タブ・配色方向を採用済み。詳細は最新の採用事項を参照 |

UI/UXは配色・書体・操作配置を目的と比較理由から決める。参考サイトの外観を模倣せず、本人の好み、一般的な知見、未検証の仮説を区別する。すべての数値を形式的に理論化する運用にはしない。

初回公開の提案範囲：閲覧、自作記事の執筆・公開管理、外部記事同期、画像、認証、バックアップ・復元、運用上の異常把握。
検索・SNS投稿連携・コメント・会員登録・複数執筆者・予約公開は初回必須に追加しない。通常のURL共有とSNS専用機能は区別する。
将来の情報収集アプリ、LINE連携、スマホアプリ等はAWS選択の背景であり、このブログの初期実装範囲ではない。

## 3. 画面と操作の設計

以下は画面の役割と機能の境界。見た目の採用値は[UI採用事項](ui-ux-decisions-current.md)、実装・受入の進捗は公開台帳で管理する。独立したページとページ内の機能を分ける。

### 独立したページ

| 画面 | 利用者・目的 | 主な内容 |
|---|---|---|
| 記事一覧 `/` | 読者が記事を選ぶ | タイトル・元公開日・媒体・遷移先、新しい順、ページ移動 |
| 自作記事本文 `/posts/{id}` | 読者が読む | タイトル・本文・初回公開日・更新日、一覧へ戻る |
| 管理 `/admin` | 本人が執筆・管理する | 未認証時はログイン、認証後は下記の管理機能 |

### 管理ページ内の機能

以下は専用ページの追加を意味しない。採用した切替・配置はUI採用事項に従い、外部同期・画像等の追加で必要な未決仕様は別途具体化する。

| 機能 | 操作と表示 |
|---|---|
| 認証 | ログイン、認証確認、失敗表示、ログアウト |
| 記事編集 | 記事選択、新規作成、Markdown、共通描画のプレビュー、保存、公開、非公開 |
| 編集内の画像挿入 | 画像ファイルの選択・認可付きアップロード、Markdownへの参照挿入、プレビュー確認。PNG/JPEG選択後、現在のカーソル位置へMarkdownを挿入 |
| 外部記事管理 | 手動同期、取得情報の補正、非表示 |
| 同期・バックアップ状態表示 | 最終成功・失敗・件数、バックアップ待ち・失敗の把握。同じ管理ページ内に表示 |

一覧の取得失敗を「記事0件」に置き換えない。下書き・非公開・存在しない記事は未認証読者に404を返す。404は存在を案内しないためであり、認証の代わりにURLを隠す設計にはしない。
現在の管理画面はJavaScriptを必要とする。SSRの対象である読者向け本文と分ける。
保存中・保存失敗・未保存を区別する。現在は手動保存のみ。記事切替・離脱・ログアウト時に未保存変更の破棄確認があるが、ブラウザー異常終了による入力消失を防ぐものではない。
PC・スマホ、キーボード、長いコード・表、失敗時の復帰を完成UIで再検証する。ローカルで一部の幅を確認しただけでアクセシビリティ全体を完了にしない。

## 4. 記事の状態と公開の意味

| 操作 | 動作 | 読者への影響 |
|---|---|---|
| 下書きを保存 | 編集内容を保存。初回は記事IDを発行する | 未公開なら公開しない。公開中なら以前の公開内容を維持 |
| 公開する | 編集内容を保存して公開へ反映。初回・更新・再公開を含む | 新しい公開内容を閲覧できる |
| 非公開にする | 公開を取りやめ、保存済みの編集内容を残す | 一覧・本文を閲覧できなくなる |

公開時の日時：初回だけ初回公開日と公開更新日を設定する。更新・再公開では初回公開日とURLを維持し、公開更新日を変更する。一覧は初回公開日順で、更新では上へ移動しない。
表示文言の案：公開中は「更新を公開する」、非公開に戻した記事は「再公開する」。共通の公開操作であり、独立した機能を増やす意味ではない。

実装では公開中かどうかと「作業版が公開版から変更されたか」を分ける。公開中＋未公開変更ありは独立した状態。
現在の「保存して公開」は保存APIと公開APIの2要求。保存成功・公開失敗なら作業版は保存済みで、以前の公開版を維持する。ひとつの原子的操作ではない。
同じversionの条件付き更新で競合を409にする。自動マージや過去版の編集履歴は未実装。
完全削除は未実装。導入する場合は明示確認と変更前バックアップ成功を条件にする。

## 5. 採用構成と選定理由

### 画面：React / TypeScript / TanStack Start、業務処理：Go

公開画面と編集画面をReactで実装し、TanStack Startで公開記事をSSRする。認証・公開判断・保存・DBアクセスはGo APIへ集約する。SSRはJavaScriptを実行しない取得元にも本文HTMLを返すために採用する。現在は要求時SSRで、ISRは採用していない。

| 比較案 | 利点 | 採用判断・負担 |
|---|---|---|
| GoのHTMLテンプレートで画面全体を生成 | HTML生成とAPIをGoへ集約できる | 単純な記事表示なら成立する。編集時の入力・プレビュー・保存状態の連動にはブラウザ側の実装が必要 |
| 公開画面はGo、編集画面はReact | 公開側のNode.jsを省ける | GoテンプレートとReactの二つの画面実装を維持する |
| 公開・編集ともReact、StartでSSR（採用） | Reactへの習熟を活かし、表示・編集の実装方法を揃える | Node.jsとGoの運用、API型の整合、初期HTMLとブラウザ表示の一致を検証する必要がある |

本人のReact習熟、編集画面の状態管理、公開画面を含む改良の一貫性を優先する。GoでもSSRやコメント等は実現できる。Reactの性能・工数優位を実測した判断ではない。コメント・いいねは初回必須にしない。

TanStack Routerは本人の学習対象・選好として採用し、そのSSR実行にStartを用いる。React RouterやNext.jsより普遍的に優れるという判断ではない。TypeScriptは画面側の型確認、GoはAPIと業務処理の学習・責務分離を目的とする。

### 基盤：AWS / ECS Fargate / RDS PostgreSQL

AWSはブログ以外のWebサービス、情報収集・LINE連携・モバイル向けAPI等を同じベンダーへ展開できる幅と、実務学習へのつながりを重視して採用する。Railway等の簡便さより、提供サービスの幅と構成の選択余地を優先した。将来の全要件に無変更で対応できる保証ではない。

| 比較案 | 今回の選定理由と受け入れる負担 |
|---|---|
| EC2 / Lightsail上の自営 | 低い固定費を狙えるが、ホストOS・更新・障害対応を自分で担う |
| ECS on EC2 | コンテナ配置はECSで管理できるが、EC2ホストの容量と保守が残る |
| ECS Fargate（採用） | コンテナの配置・更新・必要数の維持をECS、実行ホストの管理をFargateへ委ねる。常時実行の資源課金とAWS設定の管理を受け入れる。最安の選択ではない |
| PostgreSQL自営 | 費用・設定の裁量は大きいが、DB更新・障害復旧・保存基盤を自分で管理する |
| RDS PostgreSQL（採用） | 通常のリレーショナルDB構成を保ち、基盤保守を委ねる。権限・SQL移行・アプリ整合性・復元確認は自分で担う |

Aurora/MySQL等へ変更する必要性は現要件では示されておらず、採用済みPostgreSQLを維持する。全DB製品の優劣を証明した選択ではない。

### AWSの入口と配置：Node / Goの2サービス

```text
ブラウザ → HTTPS / API Gateway HTTP API
           ├─ /api・/api/* → VPC Link → Cloud Map → Goタスク → 非公開RDS
           └─ その他      → VPC Link → Cloud Map → Nodeタスク
                                                     └─ 内部DNS → Go（SSR取得）
```

NodeとGoを別ECSサービスとし、それぞれタスク定義・Cloud Map登録先を持つ。VPC Linkは共有する。ブラウザから見たオリジンは一つ。通常各1タスクを維持し、意図的なアイドル停止は行わない。

| 比較案 | 採用判断・トレードオフ |
|---|---|
| NodeとGoを同じタスクに置く | 小さく集約できるが、更新・増減・タスク停止の単位が一緒になる |
| 独立Nginx＋Node＋Goの3タスク | 高度な変換・キャッシュ等が必要なら候補。今回必要なパス分岐のために常駐費・保守・障害点を追加する利得が小さい |
| ALBからNode / Goへ直接転送 | 有力な標準構成。ただし低頻度の個人運用では入口の時間・LCU等の固定的な負担を避けたい |
| HTTP APIから2サービスへ直接転送（採用） | 各アプリを独立に更新でき、専用プロキシと独自の接続先登録処理を省ける。AWSのルート・サービス発見・通信制限の管理が必要 |
| NodeまたはGoに相手への転送を持たせる | 専用プロキシは省けるが、画面または業務APIがもう一方の通過点になる。Cookie・ヘッダー・切断等の転送責務を増やす |

タスクは常に1コンテナにする規則ではなく、ライフサイクルと独立更新の必要性で分ける。各1タスク・RDS Single-AZは高可用構成ではない。
HTTP APIの時間・送信サイズ等の制約が要件に合わなくなればALB等へ見直す。Nginxを追加しても入口の制約は消えない。画像は5MiB以内のPNG/JPEGをGo経由で検証してから非公開S3へ保存する。直接アップロードとの比較は第9節。

設定は[スタック定義](../infra/aws/validation-stack.template.json)と[AWS設定と実行手順](../infra/README.md)を参照。本番設定・配備手順の整備は公開台帳R5へ残す。

### 地域・容量

オレゴン（us-west-2）を採用する。地域選定時の同条件比較では、米国東部候補と同程度の費用で、東京AWS発の公開遅延データはオレゴンが短めだったため、費用と通信待ち時間のバランスを重視した。これは家庭・モバイル回線の実測でも現在価格の保証でもない。日本近傍の低遅延を最優先するなら東京等が比較対象となる。

検証開始値はNode 0.5vCPU/1GiB、Go 0.25vCPU/1GiB、Linux ARM64。ローカルで200記事×50KiB、一覧と本文を交互に10req/sで60秒間取得した試験では、Nodeの0.25から0.5vCPUへの増量でp95が約5.609秒から約0.095秒へ改善したため選んだ。Goは同じ0.25vCPU/1GiB、ローカルPostgreSQLとCaddy、Dockerの資源制限下での比較であり、本番の応答時間ではない。追加機能の小規模容量試験は[運用手順](../infra/production.md)に記載。実AWS全経路・同時負荷を含む必要容量は未確定。RDSはSingle-AZ db.t4g.micro / gp3 20GiBを検証値とする。本番受入の開始見積もりは運用手順に記載し、実測と許容月額で確定する。

### ローカル構成

```text
ブラウザ → Caddy :8080
           ├─ /api・/api/* → Go :8081 → PostgreSQL
           └─ その他      → Node :3000 → Go（SSR取得）
```

Caddyはローカルの同一オリジンへの経路分岐に使用し、短い設定で必要な転送を表せる。Nginxでも実現可能で、本番へCaddyを置く要件はない。Composeの各コンテナは共有ネットワーク上のサービス名で接続する。DBコンテナはローカル開発用。

### コードの責務と依存関係

```text
管理ルート → AdminPage（表示・ルーターの離脱確認）
              └─ useAdminEditor（入力・認証状態・操作の順序と結果）
                   └─ adminApi（HTTPパス・入力・応答とエラー）
                        └─ Go httpapi → blog.Store契約 → postgres（SQL）
                              └─ auth（パスワード・トークン）
公開ルート → SSR取得 → Goの公開API
本文・編集プレビュー → 共通Markdown
```

| 実装 | 責務 |
|---|---|
| [AdminPage](../frontend/src/components/AdminPage.tsx) | 採用済みの画面を表示し、操作をフックへ渡す。ルーターによる離脱確認を接続する。HTTPパスや公開操作の順序は持たない |
| [useAdminEditor](../frontend/src/features/editor/useAdminEditor.ts) | 入力、選択、認証状態、処理中、成功・失敗・結果不明を管理する。保存後の公開、再取得、確認ダイアログを含む操作の順序を扱う。公開の可否を決定する業務ルールはGoに委ねる |
| [adminApi](../frontend/src/features/editor/adminApi.ts) | Cookie付きの同一オリジン通信、APIパス・入力と応答型、HTTPエラーを扱う。Reactの状態や表示配置を持たない。型定義は実行時検証の代用ではない |
| Go httpapi / blog / postgres / auth | HTTP・認証境界、記事型と保存契約、DBアクセスと原子的な条件付き更新、暗号処理を分ける。httpapiはStore契約を介してDB保存へ依存し、画面の配色や配置へ依存しない |

一つの画面ファイルに通信と保存・公開の手順を置く案に対し、表示変更・操作フロー変更・API変更の理由が異なるため3つに分ける。単純に行数を減らす分割や、各入力ごとの細分化はしない。現在は一つの編集画面で閉じる状態のため、共有状態ライブラリや汎用的な通信基盤を追加せずReactのフックを使う。
Go側はすでにStore契約とDB実装が分かれ、公開版の保存をSQLの条件付き更新で扱っているため、記事保存だけを包むサービス層は増やさない。外部同期・画像・バックアップ・OIDCは、それぞれ固有のI/Oと失敗条件を持つため独立したパッケージと保存契約を置く。HTTPは認証と契約、postgresはトランザクション、各機能は処理の順序を担う。編集の入力・認証と、操作の `idle / running / unknown` は分けて持つ。専用状態管理ライブラリを追加する案に対し、現在は一画面の操作に閉じるため判別可能な型と共通の実行関数で扱う。

- 切替・新規・離脱・ログアウトは同じ破棄確認を使う。結果不明なら未変更の入力でも確認し、取消時は入力と未確認状態を保持する。明示して破棄した場合だけ新しい編集へ移る。
- 既存記事はIDで最新状態を取得してから開く。結果の再確認もIDで取得し、現在の入力は書き換えない。確認失敗やセッション切れ・再ログインでは未確認状態を解除しない。
- 新規編集ごとの乱数creationKeyを新規保存に付ける。同じキーと本文の再試行は同じ記事へ収束し、違う本文でのキー再利用は409。応答消失は専用APIで保存先を照合し、入力を保持する。自動再送で書き込み結果を推測しない。
- 通信は15秒で中断する。5xx・408・通信断・成功応答のJSON形式不良は、書込結果不明として扱う。4xxの拒否と区別し、JSONでないエラー応答でもHTTP状態は保持する。この期限は実行結果の保証や性能目標ではない。

### 実装上の保護・運用境界

- 生存確認とDB準備状態を分離し、DB障害だけでアプリ再起動を繰り返さない。Nodeは `/healthz`、Goは `/api/healthz` と `/api/readyz` を持つ。
- Nodeの実行入口はSSRのfetchエントリーと静的配信を接続し、API転送を担わない。SSR・静的・404・例外の外側で保護ヘッダーを適用する。
- RDS接続は `verify-full` と同梱する公開CAで署名・ホスト名を検証する。CAは公開情報であり秘密鍵ではない。更新情報は[証明書の説明](../backend/certs/README.md)を参照。
- [DB初期化](../infra/database/bootstrap.psql)は移行用DDLロールと通常アプリ用DMLロールを分離する。初期化・移行は明示的な単発タスクとし、アプリ起動より前に完了させる。
- イメージはdigestで固定し、秘密値はSSM SecureStringから役割別に注入する。管理・移行用の値を通常アプリへ渡さない。
- [疎通監視](../infra/monitoring/probe.py)はNode・API・SSRの応答を確認し、失敗と未実行を区別する。本番定義にはSNSメール購読と運用失敗ログのアラームを含める。購読先の確定・受信確認は未実施。設定の存在だけでは通知運用完了としない。CIは試験対象の監視ソースとテンプレート内の配備コピーの一致も検査する。

- 読者一覧は21件取得し、20件とhasNextを返す。旧 `/api/posts` は自作記事だけの互換API。管理一覧はページ分割なしで、規模拡大時には再検討する。

## 8. 外部記事の取り込みと選定理由

対象は本人の[Qiita](https://qiita.com/course_k)、[note](https://note.com/course__k)、[Wantedly](https://www.wantedly.com/id/course_k)。

- Qiitaは[公式API](https://qiita.com/api/v2/docs)、noteは本人のRSS、Wantedlyは本人の公開プロフィールHTML内のストーリーメタデータを使う。本文・画像は保存しない。固定された媒体・本人URLだけを取得し、任意URLの取得機能を作らない。
- 同期前のデータ取得・検証を終えてから媒体単位のトランザクションで反映し、途中失敗では既存レコードを保つ。媒体＋元IDを一意にし、手動補正と非表示は取得情報と別列で保持する。
- 日次と手動要求を同じDB上のスケジュール・期限付きリースで実行する。専用の常駐ワーカーを増やす案に対し、低頻度の3媒体なのでGoのバックグラウンド処理を使う。置換時の二重実行はリースと実行IDで防ぐ。
- noteとWantedlyは最新範囲の取得と明記する。前回取得との接点がなくなった場合は補完待ちとし、成功件数だけで全件同期と表示しない。HTML形式変更・429・通信失敗では自動連打しない。
- 公開一覧は自作・外部を同じDBクエリで並べ、21件取得して20件＋次ページ有無を返す。別々にページ分割して後から結合する案は、順序とページ境界が崩れるため採用しない。

Wantedlyは非公式HTML形式依存。[robots.txt](https://www.wantedly.com/robots.txt)だけを許諾や提供保証の根拠にしない。[利用規約](https://service-terms.wantedly.com/user_terms/ja_JP)を参照し、個人の公開記事メタデータの低頻度取得に限定する。制限を回避する取得や非公開APIの再現は行わない。

Qiitaは最大100件×20ページ、最後のページまで取得できた場合だけallとする。未認証APIの利用枠を考慮し、同期要求は最低10分空ける。通常は1日後、失敗時は1時間後へ予約し、HTTPの再送をループしない。Wantedlyは毎回robots.txtを確認し、禁止なら停止、Crawl-delayは期限付きの待機で尊重する。

実取得でQiita92件・note1件・Wantedly10件を確認した。note RSSとWantedly初期HTMLは全過去記事を保証しない。Wantedlyの古い記事を含む初回補完と、gap状態の解消手順は公開前の残件。フィードから消えた記事も自動削除しない。変更なしの同期では補正用versionを増やさず、不必要な競合を作らない。

## 9. 認証・画像・保存運用と選定理由

### 本人の認証

公開環境はAWS Cognitoの管理ログイン＋MFAを採用する。自前のパスワード認証を公開用へ拡張する案より、MFA・パスワード回復・認証側の保守を委ねられるため。GoはOIDCの署名・issuer・audience・期限・nonceを既存ライブラリで検証し、事前指定した単一のsubjectだけに管理権限を与える。ローカル専用パスワードは維持するが、HTTPS配置ではCognito設定を必須にする。

認証画面は別ウィンドウで開き、元の編集画面は入力・結果不明状態を保持したまま再ログインを確認する。ブラウザ保存領域へ記事の自動複製を増やす案に対し、一時入力の保持に限定する。管理者の回復はCognito側の回復とDBセッション失効を組み合わせ、秘密値をGitや記事バックアップへ含めない。

Cognitoの開始設定はLite・提供ログイン画面（classic）・TOTP必須・本人のemail回復・自己登録禁止。Goにはリフレッシュトークンや本人パスワードを保存しない。Cognitoに有効なログインが残っていれば再利用される場合があり、毎回のパスワード・MFA再入力を保証する設計ではない。ローカルのDBセッションはHttpOnly・SameSite Strict・HTTPS時Secure、8時間。本人subjectとの照合、別のsubject・署名不正・issuer/audience/nonce/期限不正・リプレイ拒否は署名付きテストプロバイダーで検証。実CognitoのMFA登録と回復は本番確認で扱う。

ローカルパスワードはPBKDF2-SHA256。全体10回/15分の制限には第三者が枠を使い切れる弱点があるため、公開用へ流用しない。認証失効時は管理パネルを破棄せず隠して入力を保ち、明示したログアウト時だけ破棄する。公開DBは非公開RDS、タスクSGとverify-fullで保護する。秘密値・コード・トークンはログやGitへ入れない。

### 画像

S3直接アップロード案に対し、初回は同一オリジンのGo経由で5MiB以内のPNG/JPEGを受け取り、最大1200万画素を確認して再エンコードする。EXIF等の不要なメタデータを落とし、SVG・HTML・任意形式は受け付けない。Goの処理量と入口の上限を受け入れる代わりに、署名URLの期限・完了通知・未検証オブジェクトの扱いを増やさない。

S3は非公開で、公開済み本文の画像参照をDBで照合してから配信する。作業版と公開版の参照を分け、本文と同じトランザクションで更新する。Markdownは既存のCommonMarkパーサーで解析し、コードブロックや参照形式を正規表現だけで扱わない。下書き・未添付画像は認証した本人だけが取得できる。画像単体の削除・自動GCは初回に導入しない。

ローカルは永続ボリューム、HTTPS環境はS3を必須にしてFargateの一時ファイルへ保存しない。公開・非公開の切替後も新規取得はno-storeとし、すでに読者が取得したデータを回収できるという保証はしない。

未添付・差し替え済み画像も自動削除せず、保存量に含める。S3保存後にDB応答を失った場合も、DB登録済みの可能性があるため画像を機械的に削除しない。未登録なら匿名配信されず、登録済みならバックアップ対象になる。復元用の画像コピーも削除しない。これは誤消去を避ける初回の判断であり、無制限の無償保管ではない。増加時に参照・バックアップ世代と整合するGCを検討する。

### バックアップと復元

バックアップは変更世代をDBで記録する。公開反映後は速やかに、下書き・外部記事だけの変更はDBの日付境界（標準UTC）でまとめる。変更がなければ作らない。非公開化は変更前のバックアップ成功を待ち、失敗なら503で記事を変えない。通常の再試行は15分後。公開成功とバックアップ成功は区別して画面に表示する。

pg_dump専用の実行環境を増やす案に対し、初回はアプリ管理データを一貫したDBスナップショットから論理JSONとして出力し、圧縮・ハッシュ検証し、画像本体も独立した非公開のバックアップ保存先へ複製する。認証セッション・一時リースは復元対象にしない。形式・スキーマ版を明示し、対応していない版は黙って復元しない。

DB JSONの見積もり合計64MiB、展開アーカイブ128MiBを上限にし、超過は失敗として保持・通知する。画像は1点ずつ最大5MiBで検証してコピーする。これは小規模ブログ向けの論理バックアップで、DBロール・全スキーマ・任意の旧版を戻すpg_dumpの代替全般ではない。RDS自動バックアップ7日も併用する。

開始値は取得済みアーカイブ4世代（BACKUP_RETAINで1〜30）。非公開S3は画像用とバックアップ用を分ける。本番案では旧アーカイブの非現行S3版を7日後に削除し、4世代制御で発生する保存費用を抑える。現行の画像コピーへ日数だけの削除期限を付けない。暗号化とSHA256は完全性確認に使い、WORMやアカウント侵害への保証とは扱わない。

復元は同じ移行版の空DB（名前が_testまたは_restore）と別の画像保存先へ行う。既存データがあれば中断し、セッション・ログインフローを持ち越さない。別DB・別画像先への実復元と、200記事×50KiBの作業版/公開版の復元をローカルで確認した。実RDS/S3の復元、回復に要する時間・損失許容・通知到達は未確認。[運用・本番手順](../infra/production.md)で公開前に確認する。

### 重なる観点と固有の観点

- 重なる領域：必要なコード、表現・配置、処理の整理、テストの保守性。ただし個別の推奨が一致するとは断定しない。
- リーダブルコードで詳しく扱う領域：命名、コメント、式・変数・制御フローなど、読む際の負担。
- シンプリシティで広く扱う領域：依存の将来負担、開発環境、自動化、学習、情報共有、人とのやり取り。
- モノレポの管理単位や配備境界は、両書の考え方を参考にして要件から判断する。両書が今回のディレクトリ構成を直接指定しているわけではない。

### 今回の点検単位と進行方法

以下は両書を統合したプロジェクト固有の順序。書籍そのものの章立てと区別する。

| ID | 点検対象 | 範囲・完了条件 |
|---|---|---|
| V1 | 命名 | 対象・責務・単位・条件が伝わるか。維持/変更の具体案と理由を示す |
| V2 | コメント | 説明が必要な箇所、不足、冗長、不正確な説明を区別する |
| V3 | 配置・表記・一貫性 | 関連情報の並び・段落・改行を確認。個人の好みだけで修正しない |
| V4 | 制御フロー・式・変数・状態 | 処理の流れと状態を追えるか。表現の改善と状態設計の改善を分ける |
| V5 | 関数・モジュールの責務と依存 | 目的の混在、過剰分割、重複、依存方向を具体的な変更例で評価する |
| V6 | 機能・ライブラリ・抽象化の必要性 | 必要性と便益・保守負担を比較。単なる依存数の削減を目標にしない |
| V7 | テストの可読性・保守性・保証内容 | 理解・追加の容易さと、仕様違反を検出できるかを確認する |
| V8 | 開発環境・検証手順・記録と情報共有 | 環境構築、反復作業、文書の正本、判断に必要な説明を確認する |

点検はV1〜V8の順に項目を分けて自律的に進め、通常の判断ごとに確認を求めない。各項目は、確認できた書籍の考え方、現行コードの事実、改善価値、維持/変更の提案を区別し、最後に重複する指摘と修正優先順位を統合する。要件に関わる重要な不明点だけ確認する。指摘はコード位置と根拠を示し、本文未確認の考え方は独自の提案と明示する。点検と実装の変更を分け、点検段階で修正しない。

TDDはV1〜V8と並ぶ採点項目ではなく、修正・新機能を進める作業手順として以下を適用する。各項目の進捗は公開台帳だけで管理し、別の報告書・履歴ファイルを増やさない。

### 実装・修正とテストの進め方

1. 既存コードの整理では、意図した振る舞いと対応テストを確認し、不足を補ってから動作を保って整理する。不具合まで正しい仕様として固定しない。
2. 不具合修正では、問題を再現するテストが正しい理由で失敗することを確かめ、修正して成功させる。構造整理は動作変更と区別する。
3. 新機能では、正常時・境界・失敗時の振る舞いをリストにし、一つずつテスト、実装、整理を進める。期待値は要件から決め、実装の出力をそのまま写さない。
4. テストは、目的、準備、操作、期待結果、失敗理由を読み取れるようにする。長い利用シナリオは残しつつ、重要な規則は独立して診断できるようにする。1テスト1アサーションを一律に要求しない。
5. 固定応答、実API、実DB、実ブラウザを区別する。偽物の振る舞いが本物と食い違う箇所は実DB等の契約試験で補い、模擬環境だけで結合成功としない。AWSの外部操作境界を確かめるモックは目的があるため維持する。
6. 検出力の確認は重要箇所に絞る。一時コピーで仕様を意図的に壊す等により、テストが意味のある理由で失敗するか確かめる。全コードへの機械的な適用や数値目標は設けない。

点検の判断は、対象、問題、影響、根拠、改善案、必要なテスト、優先度で示す。作業の時系列や生ログを保存せず、現在の結論・限界・残件を[進捗台帳](blog-publication-roadmap-2026-10-18.md)で管理する。
