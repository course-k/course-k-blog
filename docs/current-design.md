## 4. 記事の状態と公開の意味

| 操作 | 作業版 | 読者に見える版 | 日時・URL |
|---|---|---|---|
| 新規保存 | 新しく保存 | 非公開 | IDを発行。初回公開日は未設定 |
| 下書き保存 | 編集内容を保存 | 既存の公開版を維持 | 作業更新日時・versionのみ更新 |
| 初回公開 | 保存した作業版 | 作業版のスナップショットを公開 | 初回公開日・公開更新日を設定 |
| 更新を公開 | 保存した作業版 | 公開版を差し替え | 初回公開日・IDを維持、公開更新日を変更 |
| 非公開 | 作業版を保持 | 一覧・本文から除外 | 初回公開日・IDを保持 |
| 再公開 | 保存した作業版 | 再び公開 | 初回公開日を維持、公開更新日を変更 |

この振る舞いは初期仕様の提案を実装したもの。全て本人が個別に確定した仕様とはしない。一覧は初回公開日順とし、更新日順に上げない案。
実装では公開中かどうかと「作業版が公開版から変更されたか」を分ける。公開中＋未公開変更ありは独立した状態。
現在の「保存して公開」は保存APIと公開APIの2要求。保存成功・公開失敗なら作業版は保存済みで、以前の公開版を維持する。ひとつの原子的操作ではない。
同じversionの条件付き更新で競合を409にする。自動マージや過去版の編集履歴は未実装。
完全削除は未実装。導入する場合は明示確認と変更前バックアップ成功を条件にする。

## 5. 構成・責務・通信

### ローカルの現在の実装

```text
ブラウザー → Caddy :8080
               ├─ /api・/api/* → Go :8081 → PostgreSQL
               └─ その他 → TanStack Start/Node :3000
                                └─ サーバー側取得 → Go
```

フロントは画面・SSR・Markdown描画、Goは認証・公開状態・保存・DBアクセス、Caddyは経路分岐。管理画面からは同じオリジンのGo APIへアクセスする。
Composeではサービスごとにネットワークが別なのでサービス名で接続する。ローカルDBは開発用であり、本番DB自営への方針変更ではない。

### AWSの設計案（未配備）

```text
読者 → HTTPS/API Gateway HTTP API
     → VPC Link → Cloud Map → Fargateタスク（Caddy・SSR・Go）
                                            ├─ 非公開RDS PostgreSQL
                                            └─ 非公開S3（画像・バックアップ）
```

ECS＋Fargateの採用以外は配置の提案。RDS Single-AZ、0.5vCPU/2GiBの1タスク、DB micro/20GB、SSMから秘密値注入が候補。同一タスク内はlocalhost接続。コンテナ同居は強い権限分離ではなく、更新・増減も一緒になる。
API Gateway入口はALB固定費を避ける案だが、制約・構成要素は増える。完成HTML、Cookie、静的配信、更新時の接続を実AWSで検証する。画像の大容量送信は認証後のS3直接アップロードが候補。
本番容量・月額は未確定。過去の約49〜53ドル/月・税別は設計例の試算で、費用承認や上限保証ではない。最新料金の再調査は今回行っていない。

## 6. API：現在の実装契約

公開APIと管理APIを分離する。これは既存実装の整理であり、未実装の外部連携APIを確定するものではない。

| Method | パス | 認証 | 入力 | 成功 |
|---|---|---|---|---|
| GET | `/api/healthz` | 不要 | なし | 200 `{ok:true}`（プロセス応答） |
| GET | `/api/readyz` | 不要 | なし | 200 `{ok:true}`（DB疎通）、失敗503 |
| GET | `/api/posts` | 不要 | page=1〜10000、省略1 | 200 PublicPost配列、20件ずつ |
| GET | `/api/posts/{id}` | 不要 | 記事ID | 200 PublicPost、非公開・不存在404 |
| POST | `/api/session` | 不要 | `{password}` | 200 `{authenticated:true}`、Cookie発行 |
| GET | `/api/session` | 必須 | なし | 200 `{authenticated:true}` |
| DELETE | `/api/session` | 必須 | `{}` | 200 `{authenticated:false}`、失効 |
| GET | `/api/admin/posts` | 必須 | なし | 200 Post配列、作業更新日降順 |
| GET | `/api/admin/posts/{id}` | 必須 | 記事ID | 200 Post |
| POST | `/api/admin/posts` | 必須 | `{title,markdown}` | 201 Post |
| PUT | `/api/admin/posts/{id}` | 必須 | `{title,markdown,version}` | 200 Post |
| POST | `/api/admin/posts/{id}/publish` | 必須 | `{version}` | 200 Post |
| POST | `/api/admin/posts/{id}/unpublish` | 必須 | `{version}` | 200 Post |

- PublicPost：`id,title,markdown,publishedAt,updatedAt`。公開スナップショットを返し、作業版を返さない。現在は一覧にも本文を含むため、外部混在の一覧用データ設計で見直す候補。
- Post：`id,title,markdown,published,publishedAt,updatedAt,version,hasUnpublishedChanges`。title/markdown/updatedAtは作業版。公開版本文の列は直接JSONへ出さない。
- 日時は時刻付きJSON、画面では日本時間。IDは32バイト乱数のbase64url文字列（43文字）。タイトル変更でIDを変えない。
- エラー本文は `{error:文字列}`。入力400、認証401、Origin拒否403、未存在404、競合409、JSON以外415、ログイン試行制限429、内部失敗500。
- 更新系はOrigin完全一致とJSONを要求する。JSON上限300KiB、タイトルは空白のみ不可・最大200 Unicodeコードポイント、本文は最大256KiB。フォーム側maxlengthとの厳密なUnicode単位一致は未検証。
- 公開APIを含めCache-Controlはno-store。SSR側のGo取得は5秒タイムアウト。キャッシュの最終方針は未決。
- 一覧の次ページ有無は現在20件取得で推定するため、最終件数が20の倍数だと空の次ページがあり得る。管理一覧はページ分割なし。これらは現状の制約であり完成仕様として固定しない。

## 7. DB：現在の永続モデル

参照：[移行SQL](../backend/internal/postgres/migrations/001_initial.sql)、[保存処理](../backend/internal/postgres/store.go)。現状のテーブルは相互の外部キーを持たない。単一管理者のためユーザーテーブルはない。

| テーブル | 主な列・型 | 意味・制約 |
|---|---|---|
| posts | id text PK | 固定記事ID |
| posts | title text、markdown text | 作業版。DBもタイトル1〜200文字・本文262144バイト以下を制約 |
| posts | published_title text、published_markdown text | 最後に公開した本文のスナップショット |
| posts | published boolean | 読者に公開中か。既定false |
| posts | published_at timestamptz nullable | 初回公開日。再公開で置換しない |
| posts | public_updated_at timestamptz nullable | 公開版の更新日。公開中は公開日時と共に必須 |
| posts | updated_at timestamptz、version bigint | 作業更新日と競合検知。versionは正数、初期1 |
| sessions | token_hash text PK、expires_at timestamptz | 生トークンを保存せず有効期限を管理 |
| login_attempts | window_start bigint PK、attempts integer | 15分の時間枠ごとの全体試行数 |
| schema_migrations | version integer PK、checksum text | 明示的移行の実施履歴・改変検知 |

公開記事は公開日降順＋ID順の部分索引。セッション期限にも索引がある。接続プールは1プロセス最大5・待機2で、2タスク更新時には合計が増える。容量検証前の設定値。
DB移行は`migrate`コマンド。トランザクションとDBロックを使い、既適用SQLのチェックサム違いを拒否する。現コードは移行001だけを扱う。追加時には移行列挙の拡張が必要で、001を編集して既存DBへ再適用しない。

### 外部記事・画像・バックアップの追加モデル案

以下は未実装の論理設計であり、列名・DDL・APIの確定前にレビューする。

- 外部記事：媒体＋元記事IDを一意キー、取得したタイトル・URL・元日時・取得日時を保存。手動補正値と非表示を別に持ち、再同期で消さない。
- 統合一覧：公開自作記事＋表示対象の外部記事を元公開日で並べ、同日時は安定した補助キーで順序を固定する。
- 同期状態：媒体ごとの最終試行・成功・失敗・件数・取得範囲・補完待ちを管理。複数タスクで排他し、途中失敗を完全成功と表示しない。
- 画像：S3キー、所有・記事との関係、公開可否を判定できる情報が必要。未添付画像・公開後の差し替え・非公開化時の扱いは詳細設計待ち。
- バックアップジョブ：変更と必要なバックアップを対応付け、待機・実行・成功・失敗を再試行可能にする。世代・復元検証を別に記録する。

## 9. 認証・保護・保存運用

現在の認証は単一管理者パスワード＋DBセッションの試作。HttpOnly・SameSite Strict、HTTPS時Secure、8時間期限。パスワードはPBKDF2-SHA256でハッシュ化。公開用認証の最終方式、回復手順、強化策は未決。
全体10回/15分のログイン制限はDB共有だが、第三者が枠を使い切れる弱点がある。公開前の対処が必要。Markdownは生HTMLを許可しないが、全脅威の評価完了を意味しない。
本番DBは非公開RDSが候補。タスクSGからのみ接続しTLS検証を行う。S3は非公開、下書き画像の認可を実装して検証する。秘密値はコード・ログへ保存しない。
バックアップは公開・更新後、破壊的操作前、下書き・外部データだけ変わった日は変更をまとめて取得する案。公開の成功とバックアップ成功を分ける。破壊的操作は事前バックアップ成功を待つ。
RDS自動バックアップ7日、ダンプ4世代、復旧作業4時間は提案値。許容損失・保存世代・復旧目標は未確定。別DBへの実復元なしに運用準備完了としない。
