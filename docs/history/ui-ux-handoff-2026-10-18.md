# UI/UX担当チャットへの指示

## 目的とゴール

自分の独自ブログのUI/UXを、本人と具体案を比較しながら設計・実装してください。技術面接で説明できる成果物にもしたいですが、主目的は本人が継続して執筆し、読者が記事を探して読めるサイトです。

既存の画面は仮の試作で、見た目・文言・配置は未採用です。既存コードの見た目を正解として磨くだけでなく、利用目的から考えてください。テンプレート的な見た目を避けるためだけに奇抜にせず、情報の優先度、読む流れ、操作、文字組み、余白を選んだ理由を説明できる状態を目指します。

担当は公開ロードマップの5「UI/UX設計」と6「実装」です。AWS、Go API、DB、外部同期処理、保存運用の実装は元のチャットで進めます。

## 追加の重要方針：習慣で決めず、説明できるUI/UXにする

本人は「AIっぽい見た目」の原因として、配色・フォント・ボタン配置・レイアウトを、目的を検討せず生成時の手癖で選ぶことを問題にしています。目標は特定の色・角丸・カード等の禁止ではなく、今回の読書・執筆・記事案内の目的に照らして選択を説明できることです。個性は大切にしますが、AIらしさを避けるためだけに珍しい見た目へ置き換えないでください。

本人が挙げた参考はcatnoseさんと、Nani翻訳・Zenn・しずかなインターネットです。参考先の評価を権威としてそのまま模倣せず、実際のプロダクトや制作者自身の資料を確認し、今回と利用目的が共通する部分/異なる部分を整理してください。

catnoseさん自身の[個人サイトリニューアル記事](https://catnose.me/notes/renewed)には、複数媒体での活動を時系列にまとめるTimelineについて、その必要性と意図が書かれています。今回の複数媒体の記事案内にも関係する参考です。ただし、そこで述べられていないフォントや配置の理由まで本人の意図として創作しないでください。Nani翻訳・Zenn・しずかなインターネットの全UIを今回の元チャットで視覚的に調査済みという意味ではありません。

### 主要な選択で説明すること

| 項目 | 今回の目的と結びつけて検討する観点 |
|---|---|
| 配色 | 文章・リンク・補足・操作・失敗状態の見分け、コントラスト、本人が望む印象 |
| 書体・文字組み | 日本語と英数字/コードの読みやすさ、本文と見出しの階層、文字サイズ・行高・行長、読み込みや代替フォントの影響 |
| レイアウト・余白 | 記事選びと読書それぞれの情報の優先度、一覧性、本文への集中、PC/スマホでの流れ |
| ボタン・操作配置 | 操作頻度、保存と公開の意味、誤操作の影響、状態の分かりやすさ、タッチ/キーボード操作 |
| 媒体・リンクの表示 | 自作/外部の記事の識別、リンク先を予測できること、長いタイトルや日付の扱い |

選択は「解きたい問題→参照した知見・観察→比較案→採用理由と欠点→確認方法」のつながりを、主要な設計判断について示してください。先に慣れた見た目を作り、後からもっともらしい理論を付ける進め方にしないでください。

根拠は、(1)規格・明確なアクセシビリティ要件、(2)一般的な設計上の推奨、(3)参考先で観察した事実、(4)本人の好み、(5)今回の未検証仮説を区別します。一般的な推奨を唯一の正解として扱ったり、観察だけで制作者の意図や利用者への効果を断定したりしないでください。全てのピクセルに理論や論文が必要なわけではありません。

知見の参照先の例は、[デジタル庁のタイポグラフィ](https://design.digital.go.jp/dads/foundations/typography/)、[ボタン設計](https://design.digital.go.jp/dads/components/button/)、[W3Cのコントラスト解説](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)。該当箇所を読んで適用理由を確認し、行政サービス向けの推奨値や見た目を個人ブログへ一律に輸入しないでください。

比較案は、実際の長文・長いタイトル・技術記事のコード等で見比べ、読む/記事を選ぶ/保存する際の迷いや負担で評価します。「ミニマル」「洗練」「直感的」の形容だけで説明を済ませず、どの情報をどのように見つけやすくしたかを示してください。本人の好みを確認するところと、実装・表示検査で自律的に確認できるところを分け、細部ごとの承認待ちは増やさないでください。

## 維持する要件

- React/TypeScript、TanStack Router/Startによる読者向けSSR。Goが認証・記事・DBの処理を担当します。技術選定のやり直しは今回の目的ではありません。
- 独立したページは記事一覧、記事本文、管理の3つ。現在のパスは `/`、`/posts/{id}`、`/admin`。独自ドメインでの最終的なブログ配置は配備側と合わせ、UI担当だけで固定しません。
- 自作記事とQiita/note/Wantedlyの本人記事リンクを、元の公開日順に一つの一覧へ混在させます。媒体とリンク先が分かるようにします。外部本文の転載はしません。
- Markdownと公開記事と同じ規則のプレビューで執筆します。
- 操作は「下書きを保存」「公開する」「非公開にする」。初回・更新・再公開は共通の公開操作で、表示文言は状態に応じて検討できます。
- 公開中の下書き保存では以前の公開版を維持。更新・再公開でURLと初回公開日は変えません。一覧は元公開日順です。
- 画像挿入、外部記事管理、同期/バックアップの状態は管理内の機能です。状態表示のためだけに専用ページを増やす前提にしません。
- 検索、コメント、いいね、SNS自動投稿、会員登録、複数執筆者等を初回必須に追加しません。

## 進め方とチェックポイント

### A. 現状確認と設計の軸

既存資料と実装を読んだうえで、読者と本人それぞれの主な利用の流れを短く整理してください。既知の要件を再質問せず、不明点は結論に影響するものに絞ってまとめて聞いてください。質問を繰り返す代わりに、具体例と推奨を示して本人が判断できるようにしてください。

### B. 比較できる具体案

情報の見せ方・読書体験・編集操作に意味のある違いがある2〜3案を用意し、利点・欠点と推奨を示してください。配色だけ変えた案や説明文だけで終えず、実際に見比べられる画面案にしてください。最初は一覧と本文で方向性を選び、その方針を管理画面にも反映する進め方が候補です。

スマホ/PC、長いタイトル・コード・表・画像、自作/外部記事、保存中・失敗・未保存・公開中の未公開変更、同期失敗など、代表的な状態を扱ってください。全状態を初回の比較案へ詰め込む必要はありませんが、採用案の実装前には対応を整理します。

### C. 採用方針の記録

本人が選んだ案、比較対象、採用理由、残課題を記録します。本人の好みは本人に確認し、一般的な使いやすさと好みを混同しないでください。細かな余白や実装方法まで逐一承認を求める必要はありません。

### D. フロントエンド実装と検証

選ばれた案に沿って既存の画面を改良し、接続可能な実APIへ統合してください。公開本文のSSR、共通Markdown描画、認証と公開状態、固定URLを維持します。必要な依存追加は根拠を示し、大規模な全面書き換えを既定にしません。

PC/スマホ、キーボード、フォーカス、コントラスト、長い本文・コード・表、取得失敗と空状態、保存・公開の途中失敗を確認します。重要な利用の流れを実ブラウザで確かめ、型検査・本番ビルドと変更に必要な検証を行ってください。

フロントエンドの画面・スタイル・表示部品を担当範囲とし、API取得/型の共有部分は元のチャットとの変更衝突に注意してください。別ブランチ・必要なら別の作業ツリーで並行作業を分離し、既存の未コミット変更や他の担当の修正を消さないでください。PR作成・コミット等は既存の管理方針に従ってください。
