# 本番への反映

通常の更新は、PRの試験成功後にmainへ取り込むだけでよい。GitHub ActionsがAWSへ接続し、バックアップ・配備・本番確認を実行する。Macのログイン状態、手動の画像ドロップ、長期AWSアクセスキーには依存しない。

## 通常更新

1. PRの4ジョブ（定義、画面、Go/MySQL、通し試験）の成功を確認してmainへ取り込む。
2. `Repository checks` の `Deploy production` が自動で実行される。
3. `production_checks_passed` に対応する本番確認タスクの正常終了と、ワークフロー全体の成功を確認する。

配備対象はコミットSHAに対応するARM64イメージ。同じコミットのイメージが専用ECRにあれば再利用し、作り直さない。配備前にバックアップの成功を確認する。配置後は通常1タスク・3コンテナの正常性、実行中イメージの一致、公開HTTPSを確認する。

さらに、一時的なECSタスクで実AWSのAPIを確認する。

- 未認証管理APIの401。
- 新しい試験用記事の作成、保存、再取得。
- 10,000,000バイトのPNGとWebPについて、実際の署名付きS3 POST・CORS・完了API・正式画像登録。
- 公開前404、公開後200、非公開後404という匿名画像の公開制御。
- 同期状態の取得と、試験データの後片付け後のバックアップ。

画像のドラッグ／貼り付け等の画面操作はCI内のブラウザ試験で確認する。本番の一時タスクはAPIとS3を直接使うので、これは本番ブラウザ上の手操作やCognitoのMFA画面を毎回自動操作する試験ではない。

本番確認に失敗すると、アプリのイメージを直前のものへ戻し、ワークフローは失敗で終了する。DBのDDLは自動で巻き戻さない。

## DBまたは画像保存先の設定を変える更新

通常配備は、ソースの移行ファイルと移行処理のハッシュが、SSMの `/course-k/blog-production/applied-schema-digest` と異なる場合に停止する。この状態記録はパスワードではなく、検証済み移行コードのSHA-256。

`Reviewed production release` をmainから実行する。通常配備と同じ排他制御を使い、同時更新しない。古いmainや必要な試験が成功していないコミットでは開始しない。

1. **mode=plan** で実行する。読み取りだけで、ソースの `schemaDigest`、期待するDB版、基盤定義の変更箇所を確認する。
2. SQLをレビューし、稼働中のアプリとの後方互換性を確認する。
3. **mode=apply** を選び、planのハッシュとDB版をそのまま入力し、後方互換性の確認欄を有効にして実行する。

実行順は、変更前バックアップ → 新しい移行イメージの準備 → 移行用タスク → SQLの適用版・チェックサム確認 → 必要な画像設定 → 適用済みハッシュの記録 → アプリ配備 → 本番確認。

現在の専用ワークフローが許可する基盤変更は、移行用タスクのイメージ指定と、画像バケットのブログOrigin限定POST・`images/staging/`の1日期限だけ。他のDB・ネットワーク・IAM・バケットの公開化や置換は拒否する。これ以外の基盤変更や非互換DDLは別途設計が必要。

`check_sync=true` を明示したときだけ、Qiitaへの実際の手動同期要求と成功までを検査する。通常配備で記事を勝手に同期しない。媒体の障害、実行中、10分の制限がある場合は、成功と扱わずワークフローの結果を確認する。

## 今回すでに適用した移行002の扱い

移行002と画像設定は2026-11-08に別途適用済み。初期の状態記録には **mode=record-existing** を使い、planのハッシュとDB版2を指定する。

このモードは `migrate` を呼ばない。実DBの全移行版とSQLチェックサムが、対象イメージに含まれるSQLと一致した場合にだけ適用済みハッシュを記録する。その後、アプリ配置と自動本番確認を行う。移行・復元リハーサルを最初からやり直すための操作ではない。

## 認証・試験データ

GitHubは既存のmain限定OIDCロールを使う。CI用に本人のパスワードやMFAコードを保存しない。

本番確認タスクは、既存のアプリ実行権限で8分以内の一時セッションを作り、そのトークンをプロセス内だけで使用する。通常の管理APIを通して操作し、認証を省く公開エンドポイントは作らない。終了時にセッションを削除する。異常終了して削除できなくても期限で失効する。

各回で新しいランダムな作成要求キーを発行する。そのキーに紐づき、試験用のタイトル・本文マーカーも一致する記事と画像だけを片付ける。他の記事から参照された画像や、所有確認に失敗した記事は削除せず、試験を失敗とする。バケットの版管理は維持するため、小さな試験画像の旧版は残ることがある。10MBの元データは一時領域の期限で削除される。

## 一度だけ必要な管理者設定

`python3 scripts/aws/delivery_access.py` の定義で、既存の `course-k-blog-delivery-access` を更新する。OIDCの接続元はmain限定のまま維持する。

追加するのは、移行タスクの起動、画像バケットの限定した設定操作（CloudFormation経由のみ）、適用済みハッシュ1件の読み書き、非公開のテンプレート保管先だけ。GitHubから記事の保存先やSSMの接続秘密値を直接読める権限は追加しない。ただしアプリを配備・起動する権限は、もともと実行時データへ影響できる権限である。

CloudFormationの定義は専用の非公開・暗号化S3へ保存し、TemplateURLで渡す。51,200バイトに収めるための説明文削除を繰り返さず、S3経由の1MiB上限を検査する。保管する定義には秘密値を埋め込まず、SSM参照を維持する。テンプレートは30日で期限切れにする。

この管理者設定が未適用の場合、新しいCI/CD経路はまだ利用可能と判定しない。ローカルの本番操作者には自分やGitHubの配備権限を変更する権限を与えていない。
