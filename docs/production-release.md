# 本番への反映

通常の更新は、PRの試験成功後にmainへ取り込むだけでよい。GitHub ActionsがAWSへ接続し、未処理作業の実行・配備・本番確認を行う。Macのログイン状態や長期AWSアクセスキーには依存しない。

## 通常更新

1. PRの4ジョブ（定義、画面、Go/MySQL、通し試験）の成功を確認してmainへ取り込む。
2. `Repository checks` の `Deploy production` が自動で実行される。`frontend`・`backend`・`scripts/aws/delivery.py`・ワークフローに変更が無いpushでは配備しない。
3. ワークフロー全体の成功を確認する。

配備対象はコミットSHAに対応するARM64のNode・Goイメージ。同じコミットのイメージが専用ECRにあれば再利用し、作り直さない。配備前にAPIの関数で未処理の作業（期限の来たバックアップを含む）を実行し、成功した場合だけ進む。配置後は2つのLambda関数が新しいイメージで更新を終えたことを確かめ、CloudFrontのキャッシュを全体で無効化してから、公開HTTPSの`/healthz`・`/api/readyz`・一覧を確認する。DBが停止中なら再開を待つ。手順の詳細と配備用ロールの権限は[本番手順](../infra/production.md#githubからのアプリ更新と専用アクセス)を参照。

本番確認に失敗すると、関数のイメージを直前のものへ戻し、ワークフローは失敗で終了する。DBのDDLは自動で巻き戻さない。

本番APIとS3への直接送信（署名付きPOST・公開前後の画像の公開制御）を一時タスクで確かめる`release-check`は、Fargate時代のアプリ定義が前提だったため、現在の配備には含まれない。画像の貼り付けや公開制御はCI内のブラウザ試験で確認し、本番では切替時（2026-11-16）と画像キャッシュの確認時（2026-11-18）に手操作で確かめた。

## DBのスキーマを変える更新

通常配備は、ソースの移行ファイルと移行処理のハッシュが、SSMの `/course-k/blog-production/applied-schema-digest` と異なる場合に停止する。この状態記録はパスワードではなく、検証済み移行コードのSHA-256。

`Reviewed production release` をmainから実行する。通常配備と同じ排他制御を使い、同時更新しない。古いmainや必要な試験が成功していないコミットでは開始しない。

1. **mode=plan** で実行する。読み取りだけで、ソースの `schemaDigest` と期待するDB版を表示する。
2. SQLをレビューし、稼働中のアプリとの後方互換性を確認する。
3. **mode=apply** を選び、planのハッシュとDB版をそのまま入力し、後方互換性の確認欄を有効にして実行する。

実行順は、未処理作業の実行（バックアップを含む） → Aurora向け移行タスクの定義を候補のイメージで新しい版として登録 → その定義で`migrate` → `verify-schema`（適用版とSQLチェックサムの照合） → 適用済みハッシュの記録 → 通常と同じ関数の更新と本番確認。移行タスクの定義の通常の版はスタックの`OnDemandGoImage`に従い、関数と同時に変わるため、新しいコードが要求を受ける前にスキーマを変えるには別の版が要る。最初の接続はDBの再開を待つ。

基盤の定義（資材・権限・バケット設定）を変える更新は、このワークフローでは行わない。管理者ログインで変更セットを確かめて適用する（[本番手順](../infra/production.md)）。非互換なDDLは別途設計が要る。

**mode=record-existing** は`migrate`を呼ばない。実DBの全移行版とSQLチェックサムが対象イメージに含まれるSQLと一致した場合にだけ適用済みハッシュを記録し、関数を更新する。管理者が先に移行を済ませた場合に使う。

## 認証

GitHubは既存のmain限定OIDCロールを使う。CI用に本人のパスワードやMFAコードを保存しない。配備用ロールの定義は`python3 scripts/aws/delivery_access.py`で生成し、管理者が既存の`course-k-blog-delivery-access`スタックへ変更セットを確かめて適用する。GitHubから記事の保存先やSSMの接続秘密値を直接読める権限は持たない。ただしアプリを配備・起動する権限は、もともと実行時データへ影響できる権限である。
