# 独自ブログ：現在のタスクと次のチェックポイント
2026年10月15日更新。現在の計画台帳。過去のRailway案や「未着手」の記載より本資料を優先する。今回の依頼は整理と次作業の選定であり、アプリ・AWS設定は変更しない。

## 1. 全体ゴール
course-k.com配下の合意したブログ用URLで、自作記事をMarkdownとプレビューで執筆・公開でき、note・Qiita・Wantedlyの本人記事リンクも元の公開日順に混在するサイトを運用できる状態にする。アプリ基盤は決定済みのECS＋Fargate。意図的な無活動停止なし。
公開だけでなく、外部同期、画像の非公開保護、変更時バックアップ、復元、異常把握、更新、費用の確認まで含める。主要な設計・コード・UI/UXの判断とLLM利用・検証の記録を残し、本人が理由を説明して改良できるようにする。

## 2. 決定・設計案・未決を分ける
決定：AWSを軸にする。アプリはECS＋Fargate。React／TypeScript、TanStack Router／StartによるSSR、Go、Markdown＋プレビュー、本人記事と外部記事の混在、常時稼働。DB自営は第一候補から外す方向。
現在の設計案：非公開RDS for PostgreSQL、S3、SSR・Go・入口を1タスクへ配置、API Gateway HTTP API＋VPC Link＋Cloud Map。0.5vCPU／2GiBとDB microは検証開始候補。月約49〜53ドルは仮の利用例で、必要容量・請求上限・費用受入の確定ではない。
未決：ブログの正確なURL、UI/UXの完成案、公開用認証の最終方式、実測後の容量、課金・公開の実施判断。現在の画面・文章・色・レイアウトは試作であり、採用済みにしない。
本人の直近の意向：UI/UXは後ほど一緒に検討する。既存の見た目を既定路線とせず、利用目的・代案・選定理由・検証結果を記録する。技術ディスカッションだけを目的に機能や複雑さを増やさない。

## 4. 今後の順序と完了の証拠
第1段階：外部記事の統合と同期（次に進める作業）。
成果：自作記事と3媒体を元の公開日で一つの一覧へ出し、外部リンクへ正しく移動できる。重複・手動補正・非表示・取得失敗を扱える。
証拠：実DBへの初回登録、同一入力の再取得・同時実行、元日付順、手動修正保持、失敗時の既存データ保持を試験。媒体別の最終成功・件数・失敗を確認できる。
理由：ブログの中心要件を満たす作業で、表示情報と編集操作の形が分かるため、その後のUI/UXの具体的な比較材料になる。

第2段階：画像と保存・復元の完成。
成果：本人が画像を挿入でき、下書き画像は未認証で取得されず、記事と画像を別保存先から復元できる。
証拠：認可、再配置後の保持、変更時バックアップの成功・失敗検知、別DBと画像参照の復元。日次フルダンプへ無断で戻さず、既存の変更時方針を維持。
AWSの保存先が必要な部分はローカル検証と実S3確認を分ける。課金操作の前に作成対象・費用・削除/復旧手順をまとめる。

第3段階：UI/UXを本人と設計・検証。
成果：読者の探す・読む・外部媒体へ移動する体験と、本人の書く・保存・公開・同期管理の体験が納得できる形になる。
証拠：利用者の目的、表示する情報と優先順位、少数の具体的な代案、選定理由、PC/スマホ・キーボード等の操作確認。試作の外観に後から理由を付けて既成事実にしない。
機能の前提が固まった部分は前倒しで相談可能。すべての機能が完了するまでUIの検討を禁止する意味ではない。

第4段階：容量・公開用保護・運用条件の検証。
成果：公開する機能を含む本番相当ビルドでCPU・メモリー・DB接続・保存量・応答と料金の関係を示せる。
証拠：通常/増加データ、閲覧・編集・外部同期・ダンプが重なる試験。初期仮定の0.5vCPU/2GiBで足りるか判断し、必要なら増量後の費用も提示。認証方式、秘密情報更新、権限、失敗時の扱いも確認する。
第2・第3段階と並行して観測は進めるが、小さい現在のデータや平時のメモリーを必要容量の証明にしない。

第5段階：AWSでの配置・更新・復元を実証。
成果：ECS＋Fargate、RDS、S3、公開入口が実環境で接続し、更新・失敗復旧・通知を扱える。
証拠：HTTP APIのSSR・Cookie・画像経路、再配置、Cloud Map切替、VPC Linkの長期無通信対策、DB/管理APIの非公開境界、TLS、復元、通知。許可された課金範囲で行う。

第6段階：独自ドメインで公開し運用を引き継ぐ。
成果：本人が実URLで利用を続けられる。
証拠：承認されたDNS/公開操作、実URLでの受入確認、実記事の取り扱い、更新・同期不調・請求・復旧の短い手順。検索掲載や長期無停止を保証条件に追加しない。

## 5. 次の作業単位を限定する
次のゴール案：ローカルのブログへ本人のnote・Qiita・Wantedlyの記事リンクを登録し、自作記事と同じ時系列一覧で表示する。継続同期と失敗時の動作まで検証する。
作業案：外部記事の永続データと一意キーを追加、統合一覧API、媒体別の取得処理、初回取り込み、日次＋本人の手動同期という既存案、手動補正/非表示、同期状態の表示、DB/実画面テスト。
完了条件：媒体と外部リンクを明示。元の公開日時で安定ソート。再取得・多重実行でも重複せず、手動補正・非表示を消さず、外部障害でも既存一覧を保持。機密本文を取得・転載しない。
107件は調査時点の基準で、現在も必ず同じ件数とは決めつけない。最新取得との差・初回取り込み範囲・不足を記録する。実装確認はローカルで行い、実サイトへの外部公開はしない。
Wantedlyは非公式の公開HTML形式へ依存する候補。形式変更・取得不足を検知し、完全取得でない時は補完待ちにする。本人の自動登録希望を黙って手動へ変更しない。継続取得の条件・制約を記録し、重要な代替が必要な場合だけ本人に具体案を示す。
今回ここまでの実装を開始した扱いにはしない。計画の次の作業単位として選定した段階。アプリの既存データ・外観は変更していない。
