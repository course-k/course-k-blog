# 2タスク構成：AWS配備前レビュー

2026年10月17日。設計・設定草案・費用計算まで。

更新：[配備準備の実装・検証記録](aws-readiness-implementation-2026-10-17.md)を参照。以下の未実装記載のうち、生存確認、保護ヘッダー、RDS CA供給、DBロール準備、移行タスク、疎通・SNS通知設定は実装済み。実AWSでの確認・通知先接続とDocker再ビルドは残る。**AWS未接続・未作成、DNS/既存データ未変更、配備承認はまだ求めない。** 技術的な準備条件を解消してから、対象・金額・検証期間をまとめて確認する。

## 1. 選んだ構成と作成対象

NodeはReact SSR、Goは認証・記事管理。各1コンテナのタスクを各ECSサービスで1個常時維持。独立Nginxタスク・ALB・NAT Gateway・有料VPCエンドポイントは初期案に含めない。必要なら費用と共に再提案する。

```text
API Gateway HTTP API → VPC Link
   ├─ /api, /api/* → GoのCloud Map登録先 → Goタスク → 非公開RDS
   └─ その他 → NodeのCloud Map登録先 → Nodeタスク
                                            └─ 内部DNSでGoへ
```

[全体CloudFormation草案](../infra/review/two-task-stack.template.json)に66リソースを定義。以前の入口だけのテンプレートとは別で、二つを重ねて配備しない。

| 対象 | 設定案 | 目的 |
|---|---|---|
| VPC | 10.42.0.0/16、新規。公開2・私有2サブネット、2AZ、IGW | タスクの外向き経路、DB/VPC Linkの私有経路 |
| ECS | クラスター1、Node/Go各サービス・タスク定義 | 独立更新、通常各1タスク、更新時各最大2 |
| タスク | ARM64 Linux、各256 CPU units・1024MiB | 制限付き試験の開始値。必要容量の証明ではない |
| Cloud Map | 私有名前空間blog.internal、web/apiのA/SRV、TTL10秒 | ECSが登録先を更新。DNS名固定でIPは固定しない |
| API Gateway | API1、VPC Link1、統合2、ルート3、default stage | ブラウザーのオリジンを一つに維持 |
| SG | 入口/Node/Go/DBの4つ、受信許可4経路 | VPC Link→Node/Go、Node→Go、Go→DBのみ |
| RDS | PostgreSQL、db.t4g.micro、gp3 20GiB、Single-AZ、非公開・暗号化 | データをアプリ再配置から分離 |
| RDS保全 | 削除保護、7日自動バックアップ、削除/置換時snapshot方針 | 誤削除対策。変更時ダンプの代替完了とはしない |
| S3 | 画像用/バックアップ用2つ、非公開、TLS必須、SSE-S3、Versioning | 将来の機能の保存先。保存権限・アップロード/ダンプ機能はまだ未実装 |
| ECR | 2リポジトリ、タグ不変、scan on push、保持 | ARM64イメージの格納。リリースではdigestで参照 |
| IAM | Node/Goで実行ロールとタスクロールを分離 | NodeへDB秘密値を注入しない。初期タスクロールはAWS API権限なし |
| Secrets | RDS管理者はRDS管理のSecrets Manager秘密値1個。アプリは別のSSM SecureString2個 | アプリをDB管理者で動かさない。秘密値をテンプレートへ展開しない |
| ログ・監視 | Node/Go/Gateway各ログ14日、標準アラーム8個 | CPU/メモリー4、Gateway5xx、DB空き容量。通知先は未接続 |

各タスクの公開IPv4は外向きのイメージ取得・AWS API/外部記事アクセス用。パブリックIPがあってもSGで直接受信を許可しない。内部通信は私有IP。SGの送信は草案段階では全宛先許可で、最小受信と完全な送信先制限を混同しない。
GoはLISTEN_ADDR=0.0.0.0:8081、NodeはHOST=0.0.0.0/PORT=3000。Go→DBはverify-full DSN、Node→GoはHTTPの内部DNS。TLSを全内部ホップへ適用した設計ではない。

## 2. 月額試算

東京、月730時間、ARMオンデマンド、税別USD。Spot・長期契約・期間限定クレジットなし。10月17日に公式料金JSONを再取得し、[取得単価](aws-price-evidence-2026-10-17.json)と[計算明細](aws-two-task-costs-2026-10-17.json)を保存。

| 項目 | 月額USD・概算 |
|---|---:|
| Node/Goの計算資源（各0.25vCPU/1GiB） | 21.22 |
| タスク公開IPv4 2個 | 7.30 |
| RDSインスタンス＋20GiB | 21.01 |
| RDS管理者秘密値＋API呼出例 | 0.41 |
| DNS、Cloud Map、HTTP API | 1.47 |
| S3、ECR、ログ、8アラーム、通信・疎通予備枠 | 2.18 |
| **合計** | **53.58** |

表の各行の丸めにより合計と0.01ドル程度ずれる場合がある。
月10万HTTP要求、Cloud Map発見10万回、登録等1000回、DNS標準問い合わせ10万回の仮定。DNSは公私各ゾーンを新規計上。実際に既存公開ゾーンを使うなら0.50ドルを減らせる。API GatewayのAliasと私有DNSの問い合わせは無料なので、0.04ドルは他の有料標準問い合わせの予備であり必須費ではない。
S3は旧バージョン・全ダンプ込み6GiB、PUT等1万・GET等10万回、ECR全イメージ計2GiB、ログ取込1GiB・保存1GiB、AZ間通信10GiBを仮置き。コピー・世代・ログ増加は追加になる。
インターネット送出30GiBはAWS全体無料枠の残量がある場合。残量なしなら例では3.42ドル追加し約57.00ドル。クレジットでなく通常の共有転送無料枠の前提。ドメイン更新、CI、税・為替、復元時の追加DB、CPUクレジット超過、通常サポート外のRDS、追加スナップショットは別。RDS自動バックアップ容量が提供範囲内という前提。
SSMは標準SecureString・通常スループット・AWS管理鍵を想定。カスタマー管理KMS鍵を増やす場合は単価を加算する。RDS管理者のSecrets Managerは管理用で、アプリ接続秘密値とは別。管理者の自動回転をアプリ用資格情報へ流用しない。
疎通/通知の0.05ドルは予備費で、完成した監視システムの実測ではない。通知方式が決まったら該当サービスと単価に置き換える。

### 容量が不足した場合

- 一方だけ0.5vCPU/2GiBに増量：月約64.19ドル。
- 両方0.5vCPU/2GiB：月約74.80ドル。
- 1タスクのRAMだけ1GiB追加：月約3.23ドル追加。

これは価格感度の計算で、増量が必要と決めたものではない。RDS microも未実証。両サービス各1タスクはHA構成ではない。負荷試験・外部同期・ダンプを含むピークで容量を判断する。
単純に月額/730×24すると約1.75ドル/日だが、DNSゾーン等の月単位料金・作成/削除/保持・短時間更新等のため、短期試験の厳密な請求予測ではない。

## 3. 配備順序と、起動を止めている理由

草案のEnableRuntimeは既定false。**falseでもRDS等は作られ課金されるので、無償の確認コマンドではない。** このターンでは作成していない。

1. 課金操作前に下記の技術的前提を解消し、配備期間・削除対象・費用を提示する。
2. 承認後、新規の基盤だけを作成。既存VPC/DNS/DBは変更しない。RDSバージョンはその時点の東京の通常サポート対象を指定し、未確認の番号を埋めない。
3. ARM64イメージをECRへ格納。RDS管理者資格情報を管理用途だけに使い、専用アプリユーザーを作る。移行の権限と通常アプリ権限を分ける。DSNと管理者パスワードハッシュをSSM標準SecureStringに登録。値を履歴・ログへ出さない。
4. 単発のGo移行タスクで初期スキーマを作成。通常サービス起動の副作用にしない。
5. digest指定・秘密値ARNを入力しEnableRuntime=trueで各1タスクを起動。APP_ORIGINは検証用API Endpointを初期値に使う。独自ドメインと実記事はまだ公開しない。
6. [成立性検証](aws-two-task-validation.md)を実施し証拠を保存。独自ドメインは別途確定してACM/APIマッピング/DNSを用意する。

**配備前の技術的残件（現草案をそのまま起動しない理由）**：

- Goの生存確認をコンテナ内から実行する手段とNodeの生存専用経路。現Goイメージにcurl等はなく、架空のhealthcheckコマンドを設定していない。Cloud Mapへ正常性を反映するコンテナHealthCheckを完成させる必要がある。
- RDS CAバンドル供給・verify-fullの実接続確認。アプリDBユーザーと移行ユーザーの作成手順、必要権限、SSM設定、移行タスク定義を完成させる。
- Caddyにあるレスポンスヘッダーを失わない移設、API Gateway経由のHost/Origin・Cookie・静的ファイル・タイムアウト検証。
- 定期外部疎通（VPC Link長期無通信防止）と失敗通知先、アラーム通知を実装。現アラームは状態確認だけで通知しない。
- 不正アクセス向けの公開認証・試行制限強化は未完了。試作は本人だけで試験し、正式な実記事公開には使わない。
- イメージパラメーターは空の初期値を持つが、runtime有効化前はdigest指定を必須確認。SSM ARNは実値を含まない必須パラメーター。アカウント番号を今要求しない。

よって草案は「構成と資源をレビューできる状態」であり、本番運用の完成品ではない。アプリ側の残件を無断修正せず、必要な変更と照合して次の実装単位にする。

## 4. 更新・失敗・復元

NodeとGoを独立に更新できるが、API互換性は維持する。digestとタスク定義リビジョンを対応付ける。ローリングは100/200%、サーキットブレーカー/ロールバックを設定。初回は戻り先がないため、旧構成へ自動復帰できるとは言わない。
スキーマは既存SQLを上書きせず追加移行。破壊的操作前にバックアップを確保する。現コードは移行001のみなので、追加移行に対応する仕組みも今後必要。
RDS自動バックアップ7日は提案設定であり、公開/更新後・破壊的操作前の変更時ダンプは引き続き未実装。S3バケットを作るだけではダンプ・画像復元が成立しない。
復元時は別DBを起動し、アプリユーザーと接続先を準備、データ/画像参照と未認証保護を確認してからSSM更新・タスク再配置で切り替える。元DBは確認前に削除しない。再起動保持はバックアップ復元とは区別する。

## 5. 検証終了時の削除・費用停止

- 一時的停止：両ECSサービスを0へ。Fargate計算資源とタスクIPv4は解放後に止まるが、RDS・保存・DNS等の費用は残る。通常運用のアイドル停止方針ではなく検証終了時の操作。
- 全体撤去：DB/S3の保全を確認し、RDS削除保護を意図的に解除してからスタック削除。DBはSnapshot、S3/ECR/ログはRetain。通常の削除でデータまで自動消去しない。
- スナップショット・Retainした保存先は課金が続く。空のバケットや不要なイメージ・ログ・スナップショットは、本人確認後に個別削除。RDS管理秘密値の残存/削除状態も確認する。
- Cloud Map登録と名前空間、VPC Link、SG/ENIの解放に時間がかかり削除が失敗したら依存の解消を確認する。ECSサービス/登録先を止めずにVPCを強制削除しない。
- 現草案は独自ドメインを作成しない。手動登録したSSM値はスタック管理外なので、利用停止と保全確認後に削除対象へ含める。
- AWSの請求/リソース一覧で取り残しを確認する。スタック削除成功だけで月額ゼロと判断しない。

## 6. 今回の確認結果

全体草案を東京リージョンのcfn-lintで検査し、初回の空SSM ARNパラメーター警告を修正。構文・型・参照検査は成功。APIの入口草案も別に検査。相対リンク、費用の合計と増量感度、秘密値を含まないことを確認。
AWS validate-template・Change Set・ECS起動・実経路・RDS復元は未実施。cfn-lintは実AWSで動くことや必要権限・提供バージョン・費用を保証しない。
LLMは設定草案・既存コードとの差・単価抽出・計算と文書化に使用。AWS認証情報の参照・リソース作成・アプリ機能変更・実データ移動は行っていない。
