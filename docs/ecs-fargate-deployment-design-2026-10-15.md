# ECS＋Fargate：初期配置・運用設計案
2026年10月15日。本人決定済み：アプリ実行基盤ECS＋Fargate。以下は「進めていきましょう」に基づき具体化した設計基準案。AWSの課金リソース作成・既存設定変更・公開は行っていない。設計案の詳細を本人承認済みの要件へ置き換えない。

## 1. 初期の配置
読者／管理者→独自ドメインのHTTPS→API Gateway HTTP API→VPC Link→Cloud Map→Fargateの入口コンテナ→SSRまたはGo→RDS PostgreSQL。画像と変更時ダンプは非公開S3。
ECSサービスは通常1タスクを常時維持。Fargate ARM Linux・0.5vCPU／2GiBを検証開始枠とし、同一タスク内に入口・SSR・Goの3コンテナを置く。コンテナ数による別のFargate固定料金ではなく、タスク合計のCPU・メモリー枠で試算する。以前の2コンテナ案へ入口コンテナを追加したことは設計変更として記録する。
入口：CaddyをHTTPのリバースプロキシとして使用し、8080で受信。/apiと/api/*をGoへ、それ以外をSSRへ振り分ける。TLSはAPI Gateway側で終端する。入口に別の公開IPや追加の常時タスクを持たせない。
SSR：React／TypeScript・TanStack Router／StartのNode.jsサーバー。画面と静的アセットを返し、必要なデータはGoへ取得する。Go：認証・記事の操作・公開／非公開・外部同期・DBアクセスを担当。画面側とGoに同じ業務判定を二重実装しない。
同一タスクはネットワーク名前空間を共有するため、SSRとGoはlocalhostで通信する。GoとSSRを外部向けの待受にせず、入口のみ0.0.0.0で受ける設計。番号例はSSR3000／Go8081。最終ポートは実装時に固定する。
入口コンテナを使う理由：Node.js側にAPIプロキシ機構を埋め込む案とも比較し、HTTP経路を小さい設定へ集約して、SSR／Goの責務を保つため。管理コンテナが1つ増える欠点はある。2GiB枠に入口・SSR・Goが収まることは未実証。
SSRとGoの更新・スケールは初期は一緒。将来独立した変更頻度や負荷が生じた時にサービスを分ける。最初から独立タスクへ分割することを必須にしない。

## 2. DB・画像・機密情報
DBはRDS for PostgreSQLのSingle-AZ、db.t4g.micro・gp3 20GBを開始候補。Auroraは停止なしの最低稼働費が今回の規模で割高なため初期案から外す。DB自営は本人の直近の意向に合わせ第一候補から外す。
RDSは非公開・保存暗号化・削除保護を有効にする設計。アプリと別のリソースとして保持し、ECSサービス削除で消えないようにする。GoからTLSで接続し、証明書とホスト名の検証を行う。接続プールは小さく始め、更新時2タスクとバックアップ・移行用接続も含めて上限を測る。RDS Proxyは初期必須にしない。
RDSのバージョンは配備時に東京で対応中の通常サポート対象から固定する。バージョン番号未確認のまま実装へ記入しない。マイナー更新窓を設け、メジャー更新はアプリ互換性を検証して計画する。
S3は公開アクセスを遮断。記事画像とバックアップはバケットまたは権限単位で分ける。画像の参照可否は公開記事／下書きで認可判定する。大きな画像アップロードはGoが本人認証後に期限付きアップロード権限を発行してS3へ直接送る方式を候補とし、API Gatewayの10MB制約を回避する。サイズ・保存先制限とアップロード後検査を設ける。ダンプは読者向け画像経路へ載せない。
SSM Parameter StoreのSecureStringへDB接続情報・セッション用秘密値等を置き、ECSのsecretsで必要なコンテナだけへ注入する。通常の環境設定と機密情報を分ける。ソース・タスク定義・ログへ秘密値を直接書かない。実行ロールとアプリ用タスクロールを分け、アプリに管理者権限を与えない。
SSMからの注入は起動時なので、秘密値の更新後は新タスクへ切り替える。別コンテナもタスクの権限を共有する点を認識し、同一タスクを強い権限境界とは説明しない。カスタマー管理KMSキー等を追加するなら料金へ反映する。

## 3. ネットワークと公開入口
東京のVPCに2AZ分のサブネットを用意。RDS用は外から到達できないサブネット、Fargateは外向き通信のため公開IPv4付きの公開サブネットを使用。通常タスク1個なので2AZ同時稼働の可用性は得ない。別AZへ再配置された場合の通信費は別途測る。
タスクの公開IPを読者の接続先にはしない。受信ルールはVPC LinkのSGから入口8080だけを許可。DBのSGはタスクのSGから5432だけを許可。NAT Gatewayを置かず、イメージ取得・SSM・外部記事取得等へ直接外向き通信できる経路を取る。
Cloud MapはECSのサービス発見でタスクの私有IPと入口ポートをSRV登録し、ECSコンテナヘルスチェックと連動させる。API GatewayはVPC Link経由で登録先へ接続する。固定IPの手動更新で運用しない。初期はService Connectを重ねない。
独自ドメイン・ACM証明書・APIマッピング・$defaultおよびルートパス転送を設定する案。blog.course-k.comは以前の推奨で未決定のため、現在のドメイン直下やDNSは変更しない。SSRには外部の正しいHTTPS URLが伝わるよう、信頼する転送ヘッダーを入口で限定・正規化し、Hostやリダイレクト先を未検証入力から組み立てない。
HTTP APIの統合は30秒、ペイロード10MB。完成後のHTML配信を基準にし、ブラウザーのJavaScriptなしで本文が得られることを試験する。フレームワークがストリームを生成することと、外部まで逐次配信が保証されることを区別する。
無通信60日でVPC LinkがINACTIVEとなる仕様があるため、定期的に公開経路へ疎通リクエストを送る。月0.01ドルはスケジュール実行等の予算用留保で、実測料金ではない。実装では失敗通知まで確認する。
API Gatewayを使う理由はALBの固定費回避。ただしHTTP入口の構成要素・制約は増える。SSR・認証・応答の制約を解消できない場合だけ、ECS＋Fargateは維持して入口をALB等へ変更し、差額を明示する。

## 4. 更新・同期・バックアップ
ECRにイメージを保存し、同一コミット由来の入口設定・SSR・Goを一つのリリースとしてタスク定義へ登録する。参照を固定し、いつでも同じ組合せへ戻せる記録を残す。ローカル開発時のcomposeと本番ECSタスク定義は用途を分ける。
ECS rolling updateのminimumHealthyPercent=100／maximumPercent=200を初期案とする。通常1タスク、更新時だけ最大2タスクで、新タスクの正常性確認後に旧タスクを止める。更新中の短時間分は従量増。Cloud Mapの反映・接続切替で失敗が起きない保証はなく、更新時無停止を合格済みとはしない。
コンテナ異常とDBの一時障害は区別する。コンテナの生存確認は各プロセスが応答することを基本とし、DB障害だけで全タスクの再起動を繰り返さない。別の準備状態確認・監視でDB接続を確認する。ECSのデプロイ失敗検知・ロールバックを有効にする案。初回は戻り先がないため手動復旧手順も用意する。
DBマイグレーションは通常のアプリ起動のたびに実行しない。単発の移行処理を一度実行し、旧版と新版の両方が動く変更を基本にする。列削除等は段階を分け、破壊的操作前にダンプを確保する。アプリのロールバックとDB変更の巻き戻しは別に設計する。
外部同期はDBに最終成功時刻・状態を保持し、Goの定期処理と本人の手動実行から呼ぶ。日次という既存案を開始点とし、多重起動はDBロック等で防止。更新時2タスクでも重複登録しない。一時的なコンテナ停止で予定を逃したら再開後に追いつく。Qiita／note／Wantedlyの取得済み107件は初回確認材料で、Wantedlyの継続安定性まで実証済みとはしない。
変更時ダンプは既存方針を維持：公開・更新後、削除・一括変更・スキーマ変更前、下書き／外部情報だけ変わった日は変更日のまとめ。公開成功とバックアップ成功を同じ状態にせず、バックアップ待ち・失敗を管理側で把握できる設計にする。
ダンプの実行方法は、同一Goコンテナ内でPostgreSQL対応のpg_dumpを呼び非公開S3へ送る方式を開始案とし、非同期の再試行可能なジョブをDBへ記録する。HTTP要求を30秒間待たせない。ダンプ用依存が増える点を記録し、通常処理へ与える影響が大きい時に単発Fargateタスクへ分離する。破壊的操作は事前バックアップ完了まで実行しない。
RDSの自動バックアップ・保持7日を別の復旧経路として提案する。本人へ以前説明した毎日の自前フルダンプとは別で、RDSの管理機能。費用内の保持量を超えれば追加課金があるので計測する。ダンプ直近4世代は以前の暫定案を引き継ぎ、成功確認前に旧世代を消さない。非公開S3から別DBへ実際に復元して確認する。

## 5. 費用と公開前の合格条件
前の保存モデルの月48.88345ドル、外向き無料枠残量なしの場合52.30345ドルを計画基準にする。税・為替・ドメイン更新・有料CI・追加保存・更新時の重複・CPUクレジット超過は別。入口コンテナは既存タスク枠内なので直ちに固定費を加算しないが、実測で増量が必要なら見積もりを更新する。
試験は既存CP1案を継承：通常1リクエスト/秒10分、短時間10リクエスト/秒1分、編集と同期またはダンプの同時実行。SSR／Go／入口のメモリーとCPU、RDS接続数・メモリー・保存量、p95応答、失敗数、ダンプ所要時間を記録する。通常p95 1秒・短時間2秒などは提案目標で保証値ではない。
公開前に、HTTP API経由のHTML本文、静的アセット、404、認証Cookieと複数Set-Cookie、ログアウト、CSRF対策、下書きと下書き画像の非公開、画像アップロード、パス転送、更新時のIP変化、ロールバック、秘密値更新、変更時ダンプと別DB復元を確認する。
未実施：本番相当アプリ、負荷試験、復元試験、AWS実環境での経路・TLS試験。現環境ではDockerデーモンに接続できておらず、この計画を実証済みとは言わない。課金環境を作らず調査・設計まで完了した段階。
次のチェックポイントは、最小の閲覧・認証・記事保存経路を持つ試作で、配置と容量の仮定を検証すること。環境の用意に依存する実測は、その制約を解消してから実行する。AWSへ配備する前に作成対象・見積もり・削除／復旧手順を具体化する。未実測のまま全機能を積み上げて公開判断しない。
