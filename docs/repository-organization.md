# リポジトリ構成と保存方針

## 管理単位と採用理由

ブログという一つのプロダクトをモノレポで管理する。画面・API・DB移行・基盤設定・設計を同じ変更としてレビューでき、互換性の調整を一つのPRにまとめられるため。

| 比較案 | 判断 |
|---|---|
| frontend / backend / infra / docsのモノレポ（採用） | APIと画面の対応・設計理由を同じ履歴で管理する。ビルドは独立、本番配備はタスク単位 |
| フロント・API・基盤・文書の別リポジトリ | 独立した権限やリリースには適するが、現在の単一ブログでは対応版や変更の調整が増える |
| apps/への一括改名やNx / Turborepo等の導入 | 現在はフロントのnpmパッケージとGoモジュールが各1つで、共通パッケージもない。追加の統括層を管理する利得が小さい |

将来の別サービスは目的・リリース・権限・共有コードの有無で管理単位を判断する。同じAWSアカウントやドメインを使うだけで、このリポジトリへ追加しない。

## 配置と責務

```text
frontend/        画面・SSR・Markdown・フロント固有の検証
  src/components/       表示・ルーター接続
  src/features/editor/  編集操作のフック・管理API通信
  src/lib/              公開記事のSSR取得・共有型
  public/               題字・ロゴ・ファビコン・共通OGPの配信アセット
  assets/fonts/         記事OGPのサーバー描画用フォントと許諾
backend/         Go API・認証・DBアクセス・SQL移行・対応テスト
infra/           基盤設定・Nginx転送・DB初期化・監視とそのテスト
scripts/         再利用可能な開発・検証・配備補助
docs/            現行設計・UI設計・進捗・保存方針
.github/         PR運用設定
README.md        プロジェクト概要・機能・構成・起動の入口
compose.yaml     ローカル環境の接続設定
Caddyfile        ローカルのパス振り分け
config/          ローカル秘密値・キャッシュ・一時作業（Git対象外）
```

テストは責務の近くに置く。GoのテストはGoソースに隣接、画面・SSR試験はfrontend、監視の試験はinfraへ置く。
フロントとGoは別々にビルドし、本番はNginxを含む同じタスクで配備する。Dockerのビルドコンテキストもそれぞれのディレクトリで、docsを実行イメージやサイトへ公開しない。

## Gitへ保存する情報

| 保存するもの | 理由・更新先 |
|---|---|
| ソース・設定・移行SQL・再実行できる試験 | 動作と変更を再現・レビューするため |
| 依存lockfile | 依存解決を再現するため |
| RDS公開CAと出典 | 接続先の証明書を検証するため。秘密鍵とは異なる |
| 現行仕様と主要判断 | [設計書](current-design.md)へ選択・比較・採用理由・欠点・制約をまとめる |
| UI採用仕様と理由 | [UI設計](ui-ux-decisions-current.md)へまとめる |
| 現在の進捗と未完了事項 | [公開台帳](blog-publication-roadmap-2026-10-18.md)だけを更新する |
| 開発・配備・復旧に必要な手順 | 実行対象と前提を明確にしてREADME等へ記載する。未完成の手順を実行可能と表現しない |

会話の引用、旧計画、引き継ぎ依頼、試行錯誤や修正の順序、料金の取得データ、画面の調査ログや比較用画像を、経緯の保存だけを目的に残さない。主要な検証は結論と条件・限界を公開台帳へ要約する。試験コードは実装と一緒に管理し、一時出力を網羅して保存しない。
文書は現在の結果を更新する。日常の作業ごとに別の記録文書を増やさない。Git自体のコミット履歴を書き換える必要はない。

資格情報・秘密値・認証応答・ローカルキャッシュ・依存パッケージ・ビルド生成物はコミットしない。Git対象外であっても、再利用する配備処理をconfigだけに残さない。

## インフラ定義と運用手順の役割

| 対象 | 役割・参照先 |
|---|---|
| infra/aws/ | 共有トポロジーと検証設定例。本番版はscripts/aws/production.pyがCognito・保存権限・独自ホスト名・通知を加え、常駐部分を1タスクへ変換して生成し、巨大な定義の二重管理を避ける |
| infra/access/ | 旧検証用IAMの保存版と候補版。本番操作者はscripts/aws/production_access.py、GitHub配備用アクセス候補はscripts/aws/delivery_access.pyから別途生成する。旧検証用の適用状態と候補の差分は[検証環境の手順](../infra/README.md#使用する設定)を参照し、本番へ流用しない |
| scripts/aws/・config/ | 検証用の操作補助と本番定義の生成・契約試験。環境値・認証キャッシュ・ローカル状態・生成物はconfigへ分離。本番の実施結果は公開台帳と運用手順を参照 |
| infra/production.md | 本番配置・更新・保存/回復・認証・容量/費用の手順。実AWSでの確認は公開台帳R5/R6 |
| .github/ | 文書・基盤補助、フロント固定API、Go/実DB、実ブラウザ/SSR/API/DBの検証ワークフローとPRテンプレート。GitHubでの合否は対象PRの各ジョブを参照。マージ制限の設定は未確認。mainの全検査成功後に専用OIDC権限でアプリを自動配備 |

詳細な作業状態は公開台帳R1〜R6へ集約する。AWS試験成功を配備の完全な再現性や本番運用の完成として扱わない。

## 変更の管理

mainを共通の基準とし、作業ブランチからPRで戻す。コードと設計・対応試験を同じ変更で揃える。必要な選定理由と検証結果はPRに記載し、実装の変更を伴わない文書整理ではリンクと参照整合を確認する。
mainへのマージはデプロイや正式公開とは別。既存の未コミット変更を無関係な整理へ混ぜない。費用・公開範囲・権限・DNSに関わる操作は対象と影響を具体化して扱う。
