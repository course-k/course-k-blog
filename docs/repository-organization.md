# リポジトリ構成と情報の棚卸し

2026-10-18。対象は個人GitHubの非公開 `course-k/course-k-blog`。ソース・設定・Git追跡ファイル・ブランチ・Dockerfileを確認した。単にフォルダー名を整えるのでなく、変更の責任範囲と公開先を分ける。

## 採用する管理境界

**現行のモノレポ維持を推奨する。** ブログという一つのプロダクトのソース・インフラ設定・設計資料を同じGit履歴へ保存し、フォルダーで責務を分け、進捗台帳は1本にする。今回の整理ではこの既存構成を維持し、リポジトリ分割、ソースの大移動、新しいビルド統括ツールの導入は行わない。

| 比較案 | 利点 | 負担・今回の判断 |
|---|---|---|
| 現行のfrontend/backend/infra/docsを同じリポジトリで管理（採用） | APIと画面・DB移行・設定・設計理由を同じ変更でレビューできる | 別々のビルドと配備、対象ブランチの区別が必要。現状の単一ブログに対応する |
| フロント・Go・インフラ・文書を別リポジトリに分割 | 権限やリリース履歴を独立させやすい | 互換性・対応コミット・文書更新を複数箇所で調整する。現時点で別担当組織や別権限の必要は確認できず、負担を増やさない |
| apps/web・apps/api等へ一括改名し共通ツールを追加 | 複数アプリや共通パッケージが増えた場合に整理しやすい | 現在はGoモジュールとfrontendのnpmパッケージが各1つ。改名で参照・Docker・手順変更が必要になる一方、今回の進捗重複を直接解消しない |

同じドメインを使う将来の別サービスまで、このリポジトリへ集めると決めたものではない。独立した目的・リリース・権限・共通コードの有無で、その時点で管理単位を決める。同じAWSアカウント／ドメインと、同じリポジトリは別の判断。

## 何がどれくらい入っているか

整理前の基準コミット `cd2cb16`（feat/aws-readiness）のGit追跡ファイルを集計。合計102ファイル、2,096,512 bytes（約2.00 MiB）。これは履歴・Git内部データ・ローカル依存・AWS上の保存量を含まない。この整理による文書の追加・書き換えも含まない。集計根拠は[数量記録](repository-inventory-2026-10-18.json)。本整理では構成ガイドと数量記録の2件を追加し、整理後の追跡対象は104件（うちdocs44件）になる。

| 配置 | ファイル数 | 容量（約KiB） | 内容 |
|---|---:|---:|---|
| frontend/ | 22 | 170.9 | React/SSR、スタイル、Node実行、Docker、フロントテスト、package/lock |
| backend/ | 18 | 215.4 | Go API・認証・保存・SQL・テスト、go.mod/sum、RDS公開CA |
| infra/ | 11 | 176.5 | AWS CloudFormation、アクセス設定の版、DB初期化、疎通監視 |
| scripts/ | 4 | 10.7 | ローカル設定生成、DB/再起動検証、AWS読み取り事前確認 |
| docs/ | 42 | 1,461.0 | Markdown27、JSON12、CSV1、YAML1、ログ1 |
| ルート・.github/ | 5 | 12.9 | README、.gitignore、Compose、Caddy設定、PRテンプレート |

数量から分かること：

- 文書は42ファイルだが、Markdown本文は約271 KiB。大部分の容量は料金比較等の証拠JSONで約1.16 MiB。広域料金の1ファイルが約906 KiBを占める。
- フロントのlockfileは約142 KiB。依存の再現に使うので、容量を減らすために削除しない。
- backendの公開RDS CA証明書は約170 KiB。接続先証明書の検証に必要な公開情報で、秘密鍵とは異なる。
- 統合前の新UIブランチ `cb649c7` は118ファイル・約2.72 MiB。画面証拠PNG7枚が約742 KiB。この数字は統合前のブランチの比較記録であり、統合後のmainの数量とは分ける。ファイルの単純合算は共有ファイルを二重計上する。
- ローカルにはconfig約227 MiB、frontend/node_modules約161 MiB、dist約2.4 MiBもあるがGit対象外。これらは調査時点の例で、容量は変動する。今回削除・移動していない。

容量削減を目的に別リポジトリ・Git LFS・外部保管へ移す必要性は、現時点の量からは見いだせない。将来の画像・動画・大きなログは、増加量と用途を測って保存先を見直す。

## ディレクトリごとの保存ルール

| 配置 | 保存するもの | 保存しないもの・境界 |
|---|---|---|
| frontend/ | 画面、SSR、Markdown、フロント固有テスト、ビルド設定 | 業務の公開判断・DB秘密値・外部同期処理を重複実装しない |
| backend/ | API契約、業務処理、認証、DBアクセス、SQL移行、対応テスト | 画面の配色や配置の設定をDB仕様として増やさない |
| infra/ | 実行可能な基盤定義、DB初期化、AWSの監視処理・対応テスト | 資格情報・パスワード実値・未整理のAPI応答を置かない |
| scripts/ | 開発・検証・配備の再利用可能な補助処理 | 環境固有の秘密値や一度限りの失敗応答は置かない |
| docs/ | 現行設計、1本の台帳、主要判断、比較、選別した検証証拠 | 生の認証応答、セッション値、巨大ログ、個人の無関係な検索・画面情報を置かない |
| config/（無視対象） | ローカル秘密値、認証キャッシュ、生成物、一時作業ファイル | 唯一の再利用可能な配備実装をここだけへ残さない。Git対象外は保存の安全性を保証しない |
| ルート | リポジトリの入口、ローカル全体を接続するCompose/Caddy設定 | 詳細設計・試験の長い履歴をREADMEへ複製しない |

テストは責務の近くへ置く。GoテストはGoソースと隣接、フロントの画面/SSR試験はfrontend、監視のテストはinfraへ置き、文書に実行コードを埋め込んで唯一の実装にしない。

Dockerはfrontend/backendをそれぞれビルドコンテキストにしている。実行イメージへコピーするのはビルド結果と必要な実行ファイル・依存・公開CAで、ルートのdocsをサイトや実行イメージへ公開する構成にはなっていない。GitHub非公開、AWSでの配備対象、Webでの記事公開は別の境界。

## 文書の境界と更新先

- 進捗・未完了・次の着手点：[公開台帳](blog-publication-roadmap-2026-10-18.md)だけを更新。
- 要件、状態遷移、API、DB、アーキテクチャ：[現行設計](current-design.md)。細かな作業状態を別表へ複製しない。
- UIの採用方針：[UI採用事項](ui-ux-decisions-current.md)。比較・好みと実測を区別する。
- 主要な比較・失敗・実行結果：対象を絞った記録。日付と対象コミット、確認済み/未確認、LLM利用を残し、台帳からリンクする。
- JSON/CSV/画面証拠：結果の裏付けとして必要な範囲を選び、本文から参照する。原応答を無条件に保存しない。日付付きの料金証拠は現在価格や本番月額の正本ではない。

以前の記録はGit履歴と既存ファイルへ保持する。今回、日付付き文書には履歴である旨と台帳への案内を付け、移動によるリンク切れやUIブランチとの大量競合を避けた。将来docs/history等へ移す場合は、リンク更新とセットで行う。既存の主要判断を、形式だけ整えるために新しいADRへすべて書き直すことはしない。

## 調査基準点のブランチと再現性に関する確認事項

次のブランチ件数は整理前の調査時点の記録。統合後の共通参照先はmainとし、過去ブランチを別の完成版として扱わない。

| 対象 | 確認した状態 | 残る扱い |
|---|---|---|
| main | 641da15、初回取り込み47ファイル | 最新完成版ではない。作業ブランチの統合と受入が必要 |
| feat/aws-readiness | AWSと文書整理の作業先。今回の集計基準はcd2cb16 | 本整理後は件数が増減する。進捗正本は本ブランチの台帳 |
| feat/adopted-blog-ui | cb649c7、PR #3の採用UI | UIの実装・画像はこのブランチ。PR #3でAWS側へ統合。個別ファイルのコピーによる二重管理はしない |
| infra/review/ | 実際のAWS試験で使った定義がある | 名前だけで実行可否を判断しない。本番化時に検証用/本番用・環境パラメーターを明確化 |
| infra/access/ | 元テンプレートと管理者更新用スナップショット計4版 | 反映済みはログ修正版、スナップショット作成権限修正版は候補。元ファイルの未コミット変更は保持。無差別に一括適用しない |
| config/aws-validation/ | 一度限りのAWS実行補助や失敗応答、ローカル設定 | 再利用処理を秘密値から分離しscripts/infraへ移す残件がある。丸ごとGit追加しない |

コード・設計・試験を同じPRで対応付け、ブランチをまたぐ変更は対応コミットを明記する。自動配備はまだ定義されておらず、今回のAWS検証成功を本番配備の自動化完了として扱わない。

## 今回実施した整理と限界

READMEを入口と起動手順に絞り、台帳を現状から書き直し、索引と保存境界を整備。古い状態・次作業を正本として競合させない。履歴・検証証拠は削除せず参照できる。ブラウザ証拠ログの無関係な検索URLパラメーターは除去し、どのオリジンで警告が出たかは保持した。過去コミットのログを書き換えたものではない。

文書整理時にはアプリ実装・デプロイ・AWS設定・DB・未コミットのアクセス定義を変更していない。その後のPR統合は以下に別記する。全コードの品質監査・秘密情報の完全な履歴監査を実施したという意味ではない。

## 整理の検証・LLM利用

LLMをファイル/容量/ブランチの集計、文書の重複整理、保存境界の比較と文章化に使用。要件や採用UIの再選定はしていない。リンク到達、JSON構文、集計合計、文書の差分を検査する。アプリコード・AWS設定に変更がないため、アプリのテストを再実行した結果としては扱わない。本人が全コード・全資料をレビューしたことを意味しない。

## PRを共通のコード基準へ集約

積み上がっていたPRは、採用UIの#3→AWS対応の#2→設計を含む#1→mainという順で集約する。コードと文書を同じツリーで確認し、main反映状況は[最終の取り込みPR #1](https://github.com/course-k/course-k-blog/pull/1)で確認する。以後の作業はmainを共通の基準にし、古い3ブランチを別々の正本として使わない。未完成のブログ機能は公開台帳へ保持し、マージで完成・配備済みに変更しない。

PR #3の競合は文書4件。最新版の台帳・設計・UIの採用値を残して解消した。統合後のfrontend全追跡ファイルが元のcb649c7と一致し、backend/infraがAWS側と一致することを照合。本番ビルド・型検査、固定APIのSSR 3件、runtime 3件、Goのrace付きテスト・go vet、監視2テスト、文書リンク194件を確認。実DB結合・実ブラウザ操作を今回再実行したとは扱わない。

UI統合直後の291a2a7は122ファイル（docs54、frontend30）。[数量記録](repository-inventory-2026-10-18.json)のintegrationSnapshotに統合前との区別を保存する。今回、新しい業務コードは追加せず、ブランチ統合と文書の参照先を整えた。元のアクセス定義にある未コミット変更はハッシュ照合で保持を確認。強制push・履歴の書き換え・ブランチ削除は行わない。
