# course-k-blog

ECS＋Fargate向けの設計に沿って、閲覧→ログイン→Markdown下書き保存→公開→更新→非公開を実装したソースです。**ローカルで画面と実DBを接続した動作を確認済みです。AWS未配備で、公開用の完成版ではありません。**

## 現在の検証状態

- Go API全体のビルド成功。通常のPostgreSQLドライバーpgxを使用。メモリー保存へ切り替える起動モードはありません。
- Go自動テスト5件成功、race detector成功。HTTPテストはテスト用ストアによるハンドラー検証です。
- 実PostgreSQLテスト1件成功。保存・公開版分離・編集競合・初回公開日・再接続後の保持・セッション失効を確認。
- npmのlockfileを生成。型検査・本番ビルド・Docker内ビルド成功。提供ブラウザーツールによる実画面のログイン・保存・公開・更新・非公開・ログアウトを確認。JavaScript無効でも本文を表示。
- Compose全サービスが起動。DB・API・Web再起動後も記事内容とセッションを保持。PC/スマホの画面を確認。

## 必要な環境

Docker Compose、Node.js 24以上、Go 1.27以上、npmレジストリとGo公式プロキシへの接続。追加ネットワーク権限の承認後、Docker・localhost待受・npm取得が利用可能になりました。別の実行ターンで制限が残る場合は、必要な権限を改めて申請します。設定ファイル変更だけで解決したとは判断していません。AWSには配備していません。

## ローカル起動（確認済み）

このappディレクトリで実行します。

```sh
node scripts/setup-local.mjs
docker compose up --build
```

`http://localhost:8080` が一覧、`http://localhost:8080/admin` が管理画面です。`127.0.0.1`ではなく`localhost`で開きます。Originを厳密に照合するためです。初期設定が生成するローカル用パスワードは`config/local-login.txt`で確認します。設定ファイルを共有・公開しないでください。既存設定を自動上書きしません。

Compose内のPostgreSQLはローカル開発専用です。本番DBを自営する方針へ戻したものではありません。本番は独立した非公開RDSの設計です。ローカル専用の認証情報は初期設定スクリプトで生成済みです。再実行は不要です。

停止は`docker compose down`。データボリュームは残ります。`down -v`はDBデータを消すため、通常の停止に使いません。

## 確認する操作

1. 管理画面へログインし、タイトルとMarkdown本文を入力して下書き保存。
2. 別の未認証ブラウザーから一覧・本文に下書きが出ないことを確認。
3. 「保存して公開」で一覧と本文へ反映し、JavaScriptを無効化しても本文HTMLが読めることを確認。
4. 公開済み記事を変更して「下書きを保存」。読者には以前の本文が残ることを確認。
5. 再公開してもURLと初回公開日が変わらないことを確認。
6. 非公開に戻し、読者から取得できないことを確認。
7. ログアウト後、保存APIが拒否されることを確認。
8. Composeを再起動し、記事とログイン状態がDBから復元されることを確認。

## 構成と責務

```text
localhost:8080 → Caddy
                  ├─ /api/* → Go → PostgreSQL
                  └─ その他 → TanStack Start SSR → Go
```

- `frontend/`：画面、SSR、Markdown表示とプレビュー。生HTMLを許可するプラグインは使いません。
- `backend/internal/httpapi/`：HTTP契約、認証、Origin照合、入力制限、公開/管理用応答の分離。
- `backend/internal/blog/`：記事型と保存先の契約。
- `backend/internal/postgres/`：SQL、永続セッション、共有ログイン試行制限、明示的なDB移行。
- `scripts/`：ローカル認証情報生成とDB結合テスト。

Composeでは別のネットワーク名前空間なのでサービス名で接続します。Fargateの同一タスクではlocalhost接続に変更します。本番のGoとSSRはループバックで待受し、外部受信は入口だけにします。Composeをそのまま本番タスク定義として使いません。

## 初期判断の理由

- 公開版と作業版をDBで別列に保持：下書きの保存が読者向け本文へ漏れないため。単純な公開フラグだけの方式と比較して採用。
- バージョン番号による条件付き更新：複数タブや遅延した要求による上書きを409で拒否。最後の保存で無条件上書きする方式を採らない。
- DBにハッシュ化セッションを保存：タスク再配置後も認証を維持し、ログアウトで即時失効できるため。JWTのみ／メモリー保存と比較。
- 単一管理者のパスワード認証：縦断試作の認証を確認する最小範囲。Go標準PBKDF2-SHA256、乱数salt、定数時間比較を使用。Cognitoや外部IdPとの最終比較はまだで、公開用の認証方式が確定した扱いにしない。
- DB共有のログイン試行制限：タスクをまたいで制限を共有するため。現在は全体10回/15分で、第三者に枠を使い切られる弱点がある。公開前に対策を検証する。
- TanStack Start＋Rsbuild：既定のTanStack RouterでSSRを組み、公式ホスティング資料のNode実行経路を使う。ビルドツール自体を学習対象として増やさず、Nitroの追加を避ける。ローカルとDocker内で本番ビルド・型検査を確認。
- DB移行は独立コマンド：通常タスクの起動ごとにスキーマを書き換えない。移行履歴とチェックサムで変更済みファイルを検出。

## UI・UXの意図

読者向けは本文の読みやすさを優先し、日付・媒体表示・タイトルに絞った一覧。空の一覧は準備中と示し、通信失敗を記事0件に置き換えません。編集画面はMarkdownと同じ描画規則のプレビューを並べ、保存と公開を別操作にしています。未保存表示と離脱確認で入力消失を減らします。PC幅1280pxとスマホ幅390pxで一覧を確認し、Markdownプレビューと編集操作を確認。キーボード操作全体の監査はまだです。
